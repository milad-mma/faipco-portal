# FAIPCO Portal — کنترل تعارض قبل از ثبت مرخصی/ماموریت

تاریخ: ۱۴۰۵/۰۹/۰۳ (2026-11-24). وضعیت: نسخه آزمایشی، نیازمند آزمون روی نسخه جداگانه دیتابیس کاراوب قبل از انتشار اصلی.

## مبنا و دامنه

مبنا فایل `faipco-portal-push-reliability-twa-environment-full.zip` است (اصلاحات Push Reliability، Migration 154 و تفکیک TWA تست/اصلی حفظ شده‌اند). آخرین commit گزارش‌شده توسط کاربر از GitHub: `38544ac`. محتوای GitHub بعد از آن مستقلاً بررسی نشده است.

فقط کنترل تعارض ثبت درخواست‌های عادی مرخصی/ماموریت کاراوب (SQL Server)، تصمیم نهایی سرپرست و اعمال بعدی ساعتی اصلاح شده است. فرانت‌اند، API routeها، installer، وابستگی‌ها، سایر ماژول‌ها، اپ اندروید و migrationها تغییر نکرده‌اند. مسیرهای تردد فراموش‌شده و مجوز خروج منطق مستقل موجود را حفظ می‌کنند. داده‌های واقعی هیچ دیتابیسی تغییر نکرده است.

## مسئله

در نسخه مبنا، `_ensure_no_overlap` فقط درخواست‌های قبلی `WF_Requests` را بررسی می‌کند؛ در نتیجه ثبت مستقل منابع انسانی در `Mor_Mam` دیده نمی‌شود. مثال قطعی: پرسنل 972199، 1405/08/30، RefNumber=612500، کارت 57، Inc_Type=0 و درخواست 1350. درج هم‌کلید SQL Server 2627 رد شد و وضعیت نهایی درخواست ردشده است؛ نباید از این شواهد نتیجه گرفت خطا خودش درخواست را رد کرده است. مورد تاریخی غیبت دستی و NULL شدن گزارش بومی کاراوب رخدادی جداگانه است و هنوز علت قطعی آن اثبات نشده است.

## تغییرات

- `backend/app/services/kara_request_conflicts.py`: اعتبارسنجی مشترک درخواست فعال و کارکرد مؤثر واقعی. درخواست pending/approved متداخل مانع است؛ rejected/cancelled و انواع نقطه‌ای مستقل مانع نیستند. بازه روزانه شامل روز پایان است؛ بازه ساعتی نیمه‌باز است و عبور از نیمه‌شب لحاظ می‌شود.
- `Mor_Mam`: کنترل بازه هم‌پوشان به‌جای صرفاً تاریخ برابر، با فیلتر مصرف `Inc_Type=0/NULL` و کارت روزانه طبق منطق موجود overlay. کارت هم‌نوع نیز بررسی می‌شود. افزایش مانده ماهانه و کسورات تجمیعی با ردیف مرخصی روزانه اشتباه نمی‌شوند. نام‌های جدول و ستون از نگاشت `KaraNames` و پارامترها از placeholderهای درایور می‌آیند. بررسی همه شعب یک دیتابیس کاراوب بر مبنای قرارداد یکتایی Emp_No در همین پروژه است.
- `DataFile`: علامت‌های Status غیرصفر با بازه تردد و قواعد موجود تطبیق بررسی می‌شوند؛ Status=0 و نبود تردد به‌تنهایی مانع نیست. تطبیق تردد ساعتی با تلرانس سایت نیز بررسی می‌شود تا تردد علامت‌خورده دوباره استفاده نشود. در نبود مرز مطمئن، وضعیت متعارض یا نامطمئن با پیام مراجعه به منابع انسانی متوقف می‌شود.
- `backend/app/services/leave_request_service.py`: خواندن قفل‌دار با `UPDLOCK,HOLDLOCK` و کنترل در همان اتصال/تراکنش INSERT؛ پس از موفقیت commit انجام می‌شود، در خطا rollback. در تصمیم نهایی عادی، پس از گرفتن قفل وضعیت و داده‌های درخواست با نسخه مشاهده‌شده مقایسه، سپس تعارض واقعی بررسی می‌شود. تصمیم و اثر کارکرد در یک تراکنش SQL Server قرار دارند. رد ساده کارکرد را نمی‌نویسد. ثبت نظر WF_Reviews و ارسال اعلان همان مسیر قبلی است. اعمال بعدی درخواست ساعتی AcceptCode=8 نیز قبل از تغییر کارکرد کنترل می‌شود و در تعارض بدون اعمال باقی می‌ماند.
- پیام خطا از مسیر فعلی `LeaveRequestError` به HTTP 400 و پیام فارسی قابل نمایش در فرم می‌رسد. اعتبارسنجی هنگام کلیک «ثبت درخواست» و قبل از INSERT است، نه هنگام انتخاب تاریخ؛ endpoint جدید اضافه نشده است.
- برای بررسی معتبر در SQL Server، نگاشت `Mor_Mam` + کارت روزانه، `DataFile.Status` و `WF_Requests.AcceptCode` ضروری است. نبود نگاشت یا خطای خواندن به معنی نبود تعارض نیست و ثبت عادی را متوقف می‌کند. سایت‌های MySQL/PostgreSQL رفتار قبلی را دارند.

## آزمون‌ها و حدود قطعیت

دستور آزمون روی محیط Backend مجهز به وابستگی‌های پروژه (هیچ اتصال زنده در تست‌ها انجام نمی‌شود):

```bash
cd /var/www/html/backend
PYTHONPATH="$PWD" .venv/bin/python -m pytest -q tests/test_kara_request_conflicts.py tests/test_kara_conflict_transactions.py tests/test_leave_request_rules.py
```

در محیط تهیه بسته: 44 آزمون (25 آزمون جدید کنترل تعارض با Cursor ساختگی و 19 آزمون موجود قواعد مرخصی) موفق؛ 7 آزمون واردکردن کامل سرویس به دلیل نبود کتابخانه‌های درایور و وابستگی‌های Backend اجرا نشدند. همان 7 سناریوی تراکنش با اجرای جداگانه تعریف دقیق توابع از سورس، در محیط Mock بدون import کامل سرویس، موفق بودند. py_compile برای کد تغییرکرده موفق است. نتیجه تست Mock اثبات رفتار SQL Server واقعی، اجرای triggerها، query plan، قفل‌های واقعی و صحت محاسبه کاراوب نیست.

### معیارهای قبول در محیط جداگانه کاراوب

1. مرخصی دستی روز ۳۰ آبان یا نمونه معادل: عدم درج درخواست و عدم تغییر ردیف دستی و مانده.
2. مرخصی قبلی pending/approved، درخواست ردشده بدون اثر، و مرخصی چندروزه با تداخل جزئی.
3. مرخصی ساعتی تداخل‌دار، غیرمتداخل و شیفت شب؛ عدم استفاده دوباره از تردد دارای علامت.
4. روز عادی بدون ثبت مؤثر، تردد عادی و غیبت صرفاً محاسبه‌شده: رفتار قبلی معتبر حفظ شود.
5. HR بعد از درخواست و قبل از تأیید رکورد ناسازگار ثبت کند: تأیید متوقف، وضعیت pending، اثر دستی حفظ شود؛ رد ساده مجاز باشد.
6. همزمانی دو ثبت و دو تأیید، قطع اتصال، deadlock و شکست درج اثر: بررسی عدم تکرار یا ناهماهنگی. در صورت deadlock کاربر پیام تلاش مجدد می‌بیند؛ بررسی ایندکس‌های منبع و مدت قفل روی دیتابیس آزمایشی لازم است.
7. بازبینی گزارش بومی کاراوب، مانده و لاگ‌ها؛ اطمینان از اینکه سرور تست واقعاً به دیتابیس آزمایشی وصل است و نه دیتابیس عملیاتی.

## محدودیت‌های باقی‌مانده

- محل واقعی همه انواع «غیبت دستی» هنوز با SQL Server زنده تأیید نشده است. اگر داده از جدول دیگری یا قرارداد متفاوتی می‌آید، کنترل فعلی پوشش کامل ندارد. `DailyWork` صرفاً خروجی محاسبه/اطلاعات شیفت است و نبود تردد، غیبت دستی فرض نمی‌شود. قبل از انتشار اصلی، نمونه واقعی ثبت دستی غیبت را با دسترسی فقط‌خواندنی در کاراوب بررسی و منبعش را تعیین کنید.
- بازبینی صحت Checksum و علت NULL گزارش ماهانه، ثبت مالکیت RefNumber و ایمن‌سازی لغو/ویرایش/حذف مدیریتی، اصلاح داده تاریخی و جلوگیری از تغییرات ناسازگار بعد از پایان تراکنش توسط خود نرم‌افزار کاراوب در این مرحله انجام نشده‌اند. این بسته مجوز اجرای تغییرات روی داده واقعی یا باز کردن دوره بسته نیست.
- قفل‌ها همزمانی را در مرز تراکنش کنترل می‌کنند؛ جایگزین قرارداد مشترک با نرم‌افزار کاراوب برای تغییرات آینده HR نیستند.
- کنترل کامل نگاشت‌ها ممکن است سایت SQL Server با نگاشت ناقص را متوقف کند؛ پیش از انتشار تنظیمات را بررسی کنید. توقف امن بر پذیرش درخواست بدون بررسی اولویت دارد.
- باگ قبلی installer (تغییر کانال branch به tag هنگام اجرای داخل پوشه پروژه) در این بسته اصلاح نشده؛ سرور تست باید branch و اجرای دستور از /root داشته باشد.

## تکمیل پیام تعارض و شاهد ثبت دستی غیبت (۱۴۰۵/۰۹/۰۳)

- در آزمایش قبل و بعد از ثبت دستی برای ۴ آذر، کاراوب یک رکورد `Mor_Mam` با کارت 70، `Requested=1`، `StandardRequested=1` و `Inc_Type=NULL` و یک لاگ درج `LogMorMam` ساخت. `DailyWork` در خروجی کاربر تغییر مشهود نداشت؛ `WF_Requests` و جداول تردد خالی ماندند. در `WF_Cards` کارت 70 شعبه 1 دارای `Title=غیبت`، `DefaultTitle=مرخصی روزانه بدون حقوق 3` و `IsDay=1` است. این نوع غیبت مشمول شرط تعارض موجود است؛ این شاهد علت NULL گزارش تاریخی یا پوشش تمام انواع ثبت دستی را اثبات نمی‌کند.
- متن تأییدشده کاربر برای تعارض روزانه هنگام ثبت: «در تاریخ ۱۴۰۵/۰۹/۰۴ برای شما «غیبت» ثبت شده است. امکان ثبت درخواست وجود ندارد. لطفاً به واحد منابع انسانی مراجعه نمائید.» تاریخ و عنوان از رکورد متعارض به صورت پویا گرفته می‌شوند. عنوان از نگاشت فعلی `card_lookup_desc_column` خوانده می‌شود (برای کاراوب این سایت باید `Title` باشد، نه `DefaultTitle`). اگر شعبه هر دو جدول نگاشت شده باشد، عنوان همان شعبه رکورد انتخاب می‌شود؛ نبود عنوان یا ابهام بین عناوین مانع تشخیص تعارض نمی‌شود و پیام عمومی به کار می‌رود. در مرحله تأیید، پیام به جای «برای شما» از «برای درخواست‌دهنده» و به جای ثبت از تأیید استفاده می‌کند.
- فقط متن تعارض روزانه و خواندن عنوان به کنترل موجود اضافه شده؛ شرط تداخل، قفل و گردش کار، سایر پیام‌ها و ساختار دیتابیس تغییر نکرده‌اند. تست هدفمند جاری: 49 موفق، 7 آزمون تراکنش وابسته به درایورهای نصب‌نشده skip شدند؛ 5 آزمون جدید عنوان و متن دقیق/شعبه/فقدان عنوان/پیام تأیید را می‌سنجند. اجرای واقعی SQL روی محیط آزمایشی هنوز لازم است.

## انتشار

بسته کد را روی مخزن محلی GitHub Desktop کپی کنید، نه جایگزین کل پوشه با حذف فایل‌های قدیمی. `.git` و فایل باینری فونت موجود پروژه باید حفظ شوند. پنج فایل کد/تست/مستند در این بسته اضافه یا تغییر کرده‌اند؛ نباید فایل دیگری حذف شود. ابتدا فقط commit روی branch و آزمایش ایزوله، سپس در صورت موفقیت و تأیید پوشش غیبت دستی release tag برای محیط اصلی.

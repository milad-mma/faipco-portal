# PWA و Service Worker

## معماری Service Worker

از `vite-plugin-pwa` با استراتژی **injectManifest** استفاده می‌شود — نه
`generateSW` پیش‌فرض. تفاوت مهم: با `injectManifest`، Service Worker کاملاً
دستی خودمان (`frontend/src/sw.js`) نوشته و کنترل می‌شود (منطق کامل
Push/Notification)، فقط **فهرست Precache** (لیست فایل‌های واقعی خروجی هر
Build، با نام‌های Hash‌دار Vite) توسط Workbox خودکار داخلش تزریق می‌شود —
چون نگه‌داشتن دستی این فهرست با تغییر نام فایل در هر Build ممکن نیست.

```js
// frontend/vite.config.js
VitePWA({
  strategies: "injectManifest",
  srcDir: "src",
  filename: "sw.js",
  injectRegister: null,  // ثبت را خودمان دستی مدیریت می‌کنیم
  manifest: false,        // manifest.json را خودمان دستی نگه می‌داریم
  injectManifest: {
    globPatterns: ["**/*.{js,css,html,svg,woff,woff2}"],
  },
})
```

خروجی Build، `dist/sw.js` است — دقیقاً همان مسیری که
`frontend/src/utils/serviceWorker.js` با `register("/sw.js")` ثبتش می‌کند؛
هیچ تغییری در منطق ثبت لازم نبود.

## چرا Offline-first کامل نیست

فقط App Shell (فایل‌های JS/CSS/HTML خروجی Build) Precache می‌شوند — نه
داده‌های API. این یک پرتال مدیریتی است که برای کارکردن واقعی به اتصال زنده
نیاز دارد؛ هدف فقط جلوگیری از صفحه سفید/`ChunkLoadError` در یک قطعی
لحظه‌ای اینترنت است، نه یک تجربه کاملاً آفلاین.

**تضمین صریح**: یک Route با استراتژی `NetworkOnly` برای همه مسیرهای
`/api/*` ثبت شده — یعنی داده API هرگز حتی به‌طور تصادفی از Cache پاسخ داده
نمی‌شود، همیشه مستقیم از سرور.

## مسیریابی SPA در حالت آفلاین

چون این یک برنامه تک‌صفحه‌ای با مسیریابی سمت کلاینت است (مثلاً `/notices`
واقعاً روی سرور وجود ندارد)، از `NavigationRoute` خودِ Workbox استفاده
می‌شود تا هر درخواست ناوبری آفلاین به همان `index.html` پیش‌کش‌شده هدایت
شود.

## به‌روزرسانی — با تأیید دستی کاربر، نه Reload خودکار بی‌هشدار

`frontend/src/utils/serviceWorker.js` دو نقطه چک نسخه جدید دارد:

1. هر ۵ دقیقه، تا وقتی اپ باز است.
2. **بلافاصله** هر بار کاربر به اپ برمی‌گردد (رویداد `visibilitychange`)
   — مثلاً بعد از چند ساعت در پس‌زمینه یا باز کردن دوباره بعد از بسته‌شدن
   کامل — نه اینکه تا ۵ دقیقه بعد صبر کند.

⚠️ **مهم**: با پیداشدن نسخه جدید، Reload خودکار **اتفاق نمی‌افتد** —
`self.skipWaiting()` دیگر در `install` عمداً صدا زده نمی‌شود، نسخه جدید در
حالت "waiting" می‌ماند. به‌جایش یک رویداد سفارشی (`faipco-update-ready`)
پخش می‌شود و `UpdatePrompt.jsx` (نصب‌شده در سطح ریشه، حتی روی صفحه ورود
هم دیده می‌شود) یک پیام کوچک «نسخه جدید پرتال آماده است» با دکمه
«بارگذاری» نشان می‌دهد. فقط وقتی کاربر خودش کلیک کند، Reload اتفاق می‌افتد
— این‌طوری اگر دقیقاً همان لحظه یک فرم طولانی (مثلاً نوشتن یک اطلاعیه) باز
باشد، هیچ‌چیزی از دست نمی‌رود.

روی **اولین** نصب (نه آپدیت)، این تغییری در تجربه ایجاد نمی‌کند — چون
هیچ SW فعال قبلی برای «انتظار کشیدن» وجود ندارد، نسخه اول همان لحظه خودکار
فعال می‌شود (این محدودیت `skipWaiting` فقط برای سناریوی آپدیت معنا دارد).

`localStorage` (و در نتیجه ورود کاربر) در این فرآیند هرگز دست‌نخورده
می‌ماند — فقط کدهای فرانت‌اند تازه می‌شوند.

## حذف PWA توسط کاربر — چرا نمی‌شود واکنش نشان داد

هیچ رویداد استانداردی مثل «PWA حذف شد» برای صفحات وب وجود ندارد (عمداً،
برای حریم خصوصی). حذف یک PWA از اندروید، بسته به انتخاب کاربر، ممکن است
داده‌های Origin (Cache، localStorage، Service Worker) را هم پاک کند یا نه
— این تصمیم کاملاً دست خودِ اندروید/کروم است.

**برای تست دستی** (پاک‌کردن کامل، انگار تازه نصب شده):
اطلاعات برنامه (App Info) روی آیکون نصب‌شده → حافظه و کش (Storage) →
پاک‌کردن حافظه (Clear Storage). یا از کروم: تنظیمات سایت → دامنه پرتال →
پاک‌کردن داده و بازنشانی مجوزها.

## مقابله با Cache شدید Android روی Manifest/آیکون‌ها — نه با Query String

⚠️ **یک اشتباه واقعی که رفع شد**: نسخه قبلی این پروژه از Query String
Cache Busting (`?v=2`) روی لینک Manifest و آدرس آیکون‌ها استفاده می‌کرد.
مشکل: با این کار، Chrome روی اندروید آدرس Manifest را «متفاوت از نسخه
نصب‌شده قبلی» تشخیص می‌داد — نتیجه‌اش این بود که حتی برای کاربرانی که از
قبل PWA را نصب کرده بودند، دوباره دکمه «نصب» نمایش داده می‌شد (یعنی همان
مشکل نصب که قرار بود حل شود را در جای دیگری بدتر می‌کرد).

**راه‌حل درست**: به‌جای Query String، از خودِ هدر HTTP استفاده می‌شود —
`location = /manifest.json` در Nginx (`install.sh`) صریحاً
`Cache-Control: no-cache, must-revalidate` می‌فرستد؛ یعنی مرورگر همیشه قبل
از استفاده از نسخه Cache شده، با سرور تأیید می‌گیرد. فایل‌های `/icons/*`
هم (چون Location اختصاصی ندارند) از همین قانون در `location /` استفاده
می‌کنند. نتیجه: هم Manifest/آیکون‌ها هیچ‌وقت به‌طور خطرناکی قدیمی نمی‌مانند،
هم آدرس Manifest همیشه ثابت و قابل‌تشخیص برای Chrome باقی می‌ماند.

## CSP و PWA

هدر Content-Security-Policy (نگاه کنید `install.sh`) صریحاً `manifest-src
'self'` و `worker-src 'self'` دارد — نه فقط تکیه بر Fallback خودکارشان به
`default-src`/`script-src` — تا ثبت Service Worker و بارگذاری Manifest در
هیچ نسخه/رفتار مرورگری بلاک نشوند.

## چک‌لیست تشخیص مشکل نصب PWA روی اندروید

اگر با اینکه همه موارد بالا درست است، اپ همچنان به‌جای نصب واقعی
(WebAPK)، فقط یک میان‌بر با آیکون Chrome می‌سازد (و حتی امکان ساخت چند
میان‌بر تکراری هست — نشانه اینکه اصلاً به‌عنوان یک اپ قابل‌نصب شناخته
نمی‌شود، نه فقط دکمه اشتباه نشان داده می‌شود):

1. از Chrome DevTools (روی دسکتاپ، با اتصال به گوشی از `chrome://inspect`،
   یا مستقیم در `chrome://apps` روی گوشی) بخش **Application → Manifest**
   را چک کنید — هر خطای «Installability» دقیقاً آنجا با پیام مشخص نشان
   داده می‌شود؛ حدس‌زدن لازم نیست. پیام‌هایی مثل «Please add at least one
   screenshot...» صرفاً پیشنهاد برای ظاهر بهتر نصب هستند، نه خطای
   مسدودکننده — اگر بخش Installability هیچ خطای قرمزی نداشت، از نظر فنی
   Manifest/Service Worker کاملاً معتبرند.
2. **✅ تأیید شد (۲۰۲۶-۰۸-۱۹) — علت واقعی این پروژه**: با اینکه هیچ خطای
   فنی وجود نداشت، Chrome همچنان نصب واقعی پیشنهاد نمی‌داد. علتش
   **معیارهای رفتاری Chrome** (Engagement Heuristics) بود — بررسی
   `chrome://site-engagement` روی گوشی واقعی، امتیاز ۱۳ از ۱۰۰ را نشان داد
   (آستانه لازم برای نصب معمولاً حدود ۴۰+ است). Chrome عمداً پیشنهاد نصب
   واقعی را تا دیدن استفاده واقعی و کافی از سایت (چند بازدید در چند روز
   مختلف، نه فقط باز کردن یک‌بار) به تعویق می‌اندازد — این هیچ ربطی به
   درستی کد ندارد.

   ⚠️ **پرچم `bypass-app-banner-engagement-checks` دیگر وجود ندارد** —
   حدود ۲۰۲۳-۲۰۲۴ کاملاً از Chrome حذف شده (این پروژه هم موقع تست همین را
   تجربه کرد). راه جایگزین قطعی و تأییدشده‌ای برای Bypass این معیار پیدا
   نشد — تنها راه واقعی، استفاده طبیعی از سایت در چند بازدید/چند روز
   مختلف است تا امتیاز خودش بالا برود.

   ⚠️ **نکته مهم موقع تست**: اگر بین چند بار تست، داده/حافظه سایت را پاک
   کنید (برای شبیه‌سازی «انگار تازه نصب می‌کنم»)، Chrome کاملاً فراموش
   می‌کند که قبلاً یک Shortcut اضافه شده — یعنی هر بار اجازه اضافه‌کردن
   دوباره می‌دهد و چند آیکون تکراری روی صفحه اصلی جمع می‌شود (چون پاک‌کردن
   داده، آیکون‌های قبلی را از صفحه اصلی حذف نمی‌کند). این یک مصنوع (Artifact)
   ناشی از خودِ فرآیند تست است، نه یک باگ — برای تست تمیز، اول همه
   Shortcut های قبلی را دستی حذف کنید، بعد از آن دیگر داده پاک نکنید و
   فقط طبیعی چند روز استفاده کنید.
3. اگر دکمه «نصب» دوباره نمایش داده می‌شود برای کاربری که **از قبل نصب
   کرده**: این معمولاً یعنی آدرس `manifest.json` (یا محتوایش) بین بازدیدها
   تغییر کرده — Chrome این را به‌عنوان یک اپ «متفاوت» می‌بیند. راه‌حل: هرگز
   از Query String برای Cache Busting روی خودِ لینک Manifest استفاده
   نکنید (نگاه کنید بخش بالا) — همیشه یک آدرس ثابت بماند.

## نیاز به نصب فوری و تضمینی (بدون وابستگی به امتیاز تعامل)؟

اگر معیار رفتاری Chrome برای سناریوی شما قابل‌قبول نیست (مثلاً پرسنل
تازه‌وارد باید همان روز اول نصب کنند)، نگاه کنید
[`docs/android-app-twa.md`](android-app-twa.md) — بسته‌بندی همین PWA
به‌عنوان یک اپلیکیشن اندروید واقعی (APK)، کاملاً مستقل از این محدودیت.

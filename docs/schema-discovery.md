# کشف ساختار دیتابیس (Schema Discovery)

قابلیتی که به مدیر اجازه می‌دهد ساختار کامل دیتابیس اصلی هر سایت
(جدول‌ها، ستون‌ها، نوع‌داده‌ها، کلیدهای خارجی) را مستقیماً از پنل ادمین
ببیند - بدون نیاز به باز کردن ابزار جدا (SSMS/pgAdmin/MySQL Workbench).

## چرا این قابلیت ساخته شد

با توسعه پروژه، احتمال اتصال به دیتابیس‌های ناشناخته و متنوع بیشتری
بالا رفته - این مرحله اول (از یک طرح سه‌مرحله‌ای گسترده‌تر: کشف →
پیشنهاد بر اساس نام ستون → پیشنهاد بر اساس نمونه داده واقعی) است.
مراحل بعدی هنوز پیاده‌سازی نشده‌اند.

## نکته امنیتی/فلسفی کلیدی — این فقط «کشف»، نه «پیشنهاد» یا «اعمال»

⚠️ این قابلیت هیچ تصمیمی نمی‌گیرد و هیچ Mapping ای را خودکار پر
نمی‌کند - فقط اطلاعات خام ساختاری را نمایش می‌دهد. تصمیم این‌که کدام
ستون «کد پرسنلی» است یا کدام «تاریخ»، همچنان کاملاً دستی و توسط مدیر
گرفته می‌شود (در همان فرم‌های EmployeeMapping/AttendanceMapping
موجود). دلیل این تصمیم: حدس نادرست درباره معنای یک ستون - وقتی این
قابلیت روی Write-back (نوشتن به دیتابیس اصلی مشتری، مثل ویرایش
ایمیل/موبایل) اعمال شود - می‌تواند داده اشتباهی را در ستون کاملاً
نامرتبطی از یک دیتابیس تولید واقعی بنویسد. برای همین، این قابلیت عمداً
فقط در حد «نمایش» متوقف شده است.

## معماری Backend

### BaseSiteAdapter.discover_schema() (متد جدید انتزاعی، هر ۳ Adapter)

هر سه Adapter موجود (app/sync_engine/adapters/) این متد جدید را
پیاده کردند - هرکدام از منبع فراداده استاندارد خودشان می‌خوانند:

| دیتابیس | منبع فراداده ستون‌ها | منبع فراداده کلید خارجی |
|---|---|---|
| SQL Server | INFORMATION_SCHEMA.COLUMNS | sys.foreign_keys + sys.foreign_key_columns |
| MySQL | INFORMATION_SCHEMA.COLUMNS (با فیلتر TABLE_SCHEMA) | INFORMATION_SCHEMA.KEY_COLUMN_USAGE |
| PostgreSQL | information_schema.columns (فیلتر table_schema='public') | information_schema.table_constraints + key_column_usage + constraint_column_usage |

⚠️ نکته PostgreSQL: چون information_schema در PostgreSQL نام
ستون‌ها را کوچک برمی‌گرداند، کوئری با AS "TABLE_NAME" (گیومه‌دار،
حروف بزرگ) الیاس می‌شود - تا خروجی این Adapter دقیقاً هم‌شکل با
MSSQL/MySQL باشد.

### build_schema_dict() (تابع مشترک، در adapters/base.py)

ردیف‌های خام دو کوئری (ستون‌ها + کلیدهای خارجی) را به یک ساختار درختی
(یک ورودی به‌ازای هر جدول) تبدیل می‌کند - این تابع بین هر سه Adapter
مشترک است، برای جلوگیری از تکرار منطق.

خروجی نهایی:
```json
{
  "tables": [
    {
      "name": "kara",
      "columns": [
        {"name": "Emp_No", "data_type": "int", "nullable": false, "max_length": null}
      ],
      "foreign_keys": [
        {"column": "Emp_No", "references_table": "Personnel", "references_column": "ID"}
      ]
    }
  ]
}
```

### ⚠️ محدودیت شناخته‌شده کلیدهای خارجی

foreign_keys فقط روابطی را نشان می‌دهد که رسماً در دیتابیس به‌عنوان
Constraint ثبت شده‌اند. در بسیاری از نرم‌افزارهای قدیمی حضور و
غیاب/ERP، روابط منطقی وجود دارند (مثلاً Emp_No در جدول تردد که
واقعاً به جدول پرسنل اشاره می‌کند) بدون این‌که هرگز چنین Constraint ای
رسماً تعریف شده باشد. نبود FK در این خروجی به‌معنای نبود رابطه واقعی
نیست، فقط یعنی رسماً اعلام نشده است - این محدودیت هم در کد و هم در UI
به‌صراحت یادآوری می‌شود.

### سرویس (schema_discovery_service.py)

discover_site_schema(connection) - SiteConnection را می‌گیرد،
Adapter مناسب را (با همان adapter_factory.py موجود) می‌سازد، و
discover_schema() را صدا می‌زند.

### Endpoint

GET /sites/{site_id}/discover-schema - همان مجوز sites.manage
(site-scoped) که بقیه تنظیمات سایت دارند. اگر اتصال دیتابیس تعریف
نشده باشد، ۴۰۴ می‌دهد.

## Frontend

SchemaDiscoveryDialog.jsx - از دکمه «کشف ساختار دیتابیس» در تب
«اتصال دیتابیس» صفحه تنظیمات سایت باز می‌شود (فقط وقتی اتصال از قبل
تعریف شده باشد). یک لیست Accordion از همه جدول‌ها - هرکدام با یک جدول
ستون‌ها (نام/نوع‌داده/Nullable) و (اگر وجود داشته باشد) فهرست کلیدهای
خارجی. یک فیلد جست‌وجو برای پیداکردن سریع جدول/ستون در دیتابیس‌های با
تعداد جدول زیاد.

## مراحل بعدی (هنوز پیاده‌سازی نشده)

طبق طرح توافق‌شده، دو مرحله بعدی که می‌توانند روی همین زیرساخت ساخته
شوند:

1. **پیشنهاد بر اساس نام ستون**: تطبیق نام ستون‌های کشف‌شده با یک
   دیکشنری الگو (فارسی+انگلیسی) برای هر مفهوم مورد نیاز (کد پرسنلی،
   ایمیل، موبایل، تاریخ، ...) و پیشنهاد پرکردن خودکار فرم Mapping - با
   درصد اطمینان، همیشه قابل‌ویرایش/رد توسط مدیر.
2. **پیشنهاد بر اساس نمونه داده واقعی**: برای ستون‌های مبهم، چند مقدار
   نمونه واقعی خواندن و تشخیص الگو (مثلاً «مقادیر ۸ رقمی بین محدوده
   منطقی یعنی احتمالاً تاریخ شمسی فشرده»).

هر دو مرحله همچنان طبق همان اصل بالا، فقط پیشنهاد می‌دهند، هرگز
خودکار اعمال نمی‌کنند - تأیید نهایی همیشه دستی و توسط مدیر باقی
می‌ماند.

## مرحله دوم — پیشنهاد نگاشت بر اساس نام ستون

بعد از کشف ساختار (مرحله اول)، الان می‌شود برای هر جدول کشف‌شده،
پیشنهاد خودکار برای نگاشت گرفت - بدون نیاز به تایپ دستی نام ستون‌ها.

⚠️ همان اصل مرحله اول: این فقط پیشنهاد است، هیچ داده‌ای نمی‌خواند
(حتی داده نمونه - آن مرحله سوم است)، و هیچ Mapping ای را بدون تأیید
صریح مدیر ذخیره نمی‌کند.

### الگوریتم (`mapping_suggestion_service.py`)

یک الگوریتم خالص (بدون I/O، کاملاً قابل‌تست) - برای هر «مفهوم»
موردنیاز (کد پرسنلی، ایمیل، موبایل، تاریخ، ساعت، تاریخ/ساعت ورود،
تاریخ/ساعت خروج)، یک دیکشنری کلیدواژه (فارسی+انگلیسی) در دو سطح
اطمینان تعریف شده:

- **بالا**: نام‌های رایج و اختصاصی (مثل `emp_no`، `personnel_code`،
  `enter_date`) - شانس تطبیق تصادفی با یک ستون نامرتبط پایین.
- **متوسط**: کلیدواژه‌های عمومی‌تر (مثل `date`، `phone`) - ممکن است با
  ستون‌های نامرتبط هم تصادفاً هم‌خوانی داشته باشند.

برای هر ستون کشف‌شده، نام آن نرمال‌سازی می‌شود (حذف `_`/فاصله، تبدیل
به حروف کوچک) و با نسخه نرمال‌شده هر کلیدواژه مقایسه می‌شود - یا تطبیق
دقیق (اولویت بالاتر) یا شامل‌بودن جزئی. اگر هیچ کلیدواژه‌ای (حتی سطح
متوسط) با هیچ ستونی هم‌خوانی نداشت، `None` برمی‌گردد - **سکوت همیشه
بهتر از یک پیشنهاد نادرست است**.

هشت تست واحد (`tests/test_mapping_suggestion_service.py`) این منطق
را با سناریوهای واقعی (جدول `kara` کلاسیک، حالت ورود/خروج جدا، نام‌های
فارسی) و مهم‌تر از همه یک تست صریح برای «ستون‌های کاملاً مبهم/کدگذاری‌شده
باید هیچ پیشنهاد غلطی نگیرند» تأیید می‌کند.

### Endpoint

`POST /mapping-suggestions` - ورودی: `{"columns": [...], "concepts": [...]}`،
خروجی: یک نگاشت از هر مفهوم به بهترین ستون پیشنهادی (یا `null`).
⚠️ عمداً به `site_id` نیاز ندارد و هیچ اتصال دیتابیسی برقرار نمی‌کند -
چون Frontend نام ستون‌ها را از قبل (مرحله کشف) در اختیار دارد؛ این فقط
یک الگوریتم محاسباتی محض است.

### Frontend

`SchemaDiscoveryDialog.jsx`: هر جدول کشف‌شده حالا یک بخش «پیشنهاد
نگاشت برای این جدول» دارد - انتخاب نوع نگاشت (پرسنل / تردد یک‌ستونی /
تردد ورود-خروج جدا) + دکمه «دریافت پیشنهاد». نتیجه با سطح اطمینان
(بالا/متوسط، با رنگ متفاوت) نمایش داده می‌شود؛ دکمه «اعمال این
پیشنهادها به فرم نگاشت» مقادیر را روی فرم `EmployeeMapping`/
`AttendanceMapping` موجود در `SiteSettingsPage.jsx` می‌گذارد و به تب
مربوطه سوییچ می‌کند - **ذخیره واقعی همچنان نیازمند کلیک صریح روی دکمه
«ذخیره» موجود است**.

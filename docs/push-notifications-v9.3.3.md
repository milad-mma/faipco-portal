# FAIPCO v9.3.3 — اصلاح ارسال Push، تکرار اعلان نامه و خروج از حساب

پایه: FAIPCO v9.3.2، با حفظ سایر ماژول‌ها.

## علت مشکلات مشاهده‌شده

- در v9.3.2 رویداد OA پس از شکست ارسال به *یکی* از اشتراک‌ها، Push را برای **همه اشتراک‌ها** تکرار می‌کرد. در داده‌های واقعی کاربران 203 و 271، پنج رویداد به سقف ۱۰ تلاش رسیده بودند؛ بخشی از دستگاه‌ها در هر تلاش موفق بودند.
- خروج از حساب نشست را باطل می‌کرد اما اشتراک Push مستقل از نشست نگهداری می‌شد. لذا دستگاه خارج‌شده همچنان می‌توانست اعلان بگیرد.
- Service Worker از `Date.now()` برای شناسه اعلان استفاده می‌کرد؛ هر تکرار به صورت اعلان مجزا نمایش داده می‌شد.

## اصلاحات

1. `push_subscriptions.session_id` با FK به `user_sessions` افزوده شد (Migration 153). ارسال تمام Pushهای عمومی و OA صرفاً برای اشتراک‌های دارای **نشست فعال، منقضی‌نشده و کاربر فعال** صورت می‌گیرد.
2. اشتراک‌های قدیمی عمداً **بدون session_id** باقی می‌مانند؛ **بدون حذف داده**، دیگر اعلان دریافت نمی‌کنند تا مرورگرِ در حال ورود، با احراز هویت، همان endpoint را دوباره ثبت و به نشست معتبر وصل کند. ورود به پنل/بازکردن مجدد پنل با مجوز اعلان فعال، این ثبت را خودکار انجام می‌دهد. روی دستگاه‌های کاملاً بسته، دریافت Push موقتاً قطع می‌شود تا کاربر پرتال را باز کند؛ این یک انتخاب امنیتی برای جلوگیری از Push روی نشست‌های نامعلوم است.
3. ثبت endpoint از `INSERT ... ON CONFLICT DO UPDATE` استفاده می‌کند تا دو فراخوانی همزمان هنگام Login و Layout خطای Unique Constraint ندهند و به نشست نادرست متصل نشوند.
4. هر رویداد OA در `oa_notification_outbox.payload._delivery` فهرست اشتراک‌های **ارسال‌شده، منقضی/حذف‌شده و هنوز ناموفق** را نگه می‌دارد. در تلاش بعدی فقط باقی‌مانده‌ها هدف هستند. نتیجه جزئی **قبل از زمان‌بندی تلاش مجدد** در دیتابیس commit می‌شود. حداکثر ده تلاش محفوظ است؛ صف پایدار و قفل PostgreSQL SKIP LOCKED حذف نشده‌اند.
5. هنگام خروج همان نشست، خروج از راه دور، خروج از سایر نشست‌ها، ابطال ادمین، تغییر رمز، رسیدن به سقف نشست‌ها و انقضا، اشتراک‌های متعلق به نشست باطل‌شده حذف یا در کوئری ارسال فیلتر می‌شوند. فقط دستگاه‌های مرتبط تحت تأثیر قرار می‌گیرند.
6. ارسال Push شامل `session_marker` (شناسه نشست غیرمحرمانه) است. Service Worker فقط وقتی اعلان را نمایش می‌دهد که marker پیام با نشست تأییدشده و ثبت‌شده این مرورگر مطابقت داشته باشد. هنگام Logout مجوز نمایش محلی قطع و اعلان‌های باز بسته می‌شود. Pushهای قدیمی بدون marker در SW جدید نمایش داده نمی‌شوند.
7. برای هر رویداد OA شناسه `notification_key` ثابت داخل Push قرار می‌گیرد. Service Worker با IndexedDB دریافت رویداد را حتی پس از بسته‌شدن اعلان ثبت می‌کند و از نمایش دوباره آن جلوگیری می‌کند. Pushهای عمومی همچنان رفتار رویدادی اصلی خود را دارند.
8. لاگ خطا به‌جای آدرس endpoint یا کلیدهای حساس، شناسه اشتراک و ارائه‌دهنده را ثبت می‌کند. «دستگاه‌های من» اکنون وضعیت فعال‌بودن Push هر نشست را نشان می‌دهد.

## نصب / مهاجرت

- **ابتدا** از PostgreSQL و فایل‌های پروژه نسخه پشتیبان بگیرید.
- کد این بسته را جایگزین کد نسخه 9.3.2 کنید. فایل `.env` تولیدی سرور و فایل‌های ضمیمه را بازنویسی نکنید.
- در پوشه `backend` و محیط پایتون آماده، `alembic current` سپس `alembic upgrade head` را اجرا کنید. Head این بسته `153` است. این Migration فقط یک ستون، کلید خارجی و ایندکس اضافه می‌کند و اشتراک‌های قدیمی را حذف نمی‌کند.
- Backend را Restart و Frontend را مجدداً Build/Deploy کنید (`npm ci` یا `npm install` سپس `npm run build` مطابق فرایند استقرار فعلی).
- برای فعال‌شدن منطق Service Worker جدید، کاربران باید **نسخه جدید PWA** را به‌روزرسانی کنند. کاربرانِ دارای نشست فعال و مجوز اعلان granted با بازکردن پرتال، اشتراک را مجدداً ثبت می‌کنند.
- **هرگز پنج رویداد قدیمی failed را صرفاً برای تست به pending تغییر ندهید**: ممکن است موجب ارسال مجدد پیام قدیمی شود؛ آن‌ها به‌عنوان سوابق باقی می‌مانند.

## کنترل بی‌خطر پس از استقرار

```sql
-- میزان اتصال اشتراک‌ها به نشست‌ها؛ پس از بازکردن پرتال روی دستگاه‌های فعال، bound افزایش می‌یابد.
SELECT CASE WHEN session_id IS NULL THEN 'legacy_inactive' ELSE 'session_bound' END AS category,
       count(*) AS count
FROM push_subscriptions
GROUP BY category;

-- وضعیت صف و میزان ارسال مجدد
SELECT status, count(*) AS total, max(attempts) AS max_attempts
FROM oa_notification_outbox
GROUP BY status ORDER BY status;

-- پنج رویداد قدیمی failed خودکار دوباره ارسال نمی‌شوند.
SELECT id, status, attempts, payload->'_delivery' AS per_device_progress
FROM oa_notification_outbox ORDER BY id DESC LIMIT 30;
```

## محدودیت‌های صریح

- تحویل موفق Web Push به **درگاه FCM/Apple** به معنی مشاهده نهایی توسط کاربر نیست. برنامه نمی‌تواند تحویل قطعی سیستم‌عامل را تضمین کند.
- همانند دیگر صف‌های «حداقل یک بار»، قطع فرآیند *دقیقاً بین پذیرش Push توسط ارائه‌دهنده و ثبت نتیجه در PostgreSQL* می‌تواند یک ارسال تکراری ایجاد کند؛ شناسه ثابت/داده IndexedDB نمایش مجدد همان رویداد را در Service Worker جدید کاهش می‌دهد.
- Pushای که **قبل از خروج از راه دور به درگاه خارجی تحویل داده شده** را نمی‌توان از درگاه پس گرفت. Logout محلی در Service Worker جدید آن را مسدود می‌کند؛ برای دستگاهی که قبلاً از راه دور باطل شده و هنوز از نسخه قدیمی Service Worker استفاده می‌کند، اعلان ذخیره‌شده قدیمی می‌تواند باقی بماند. محتوای Push باید فاقد موضوع/متن محرمانه نامه باشد (مطابق طراحی فعلی).
- تست‌های unit/mock و اعتبارسنجی زنجیره migration انجام شده‌اند، ولی اتصال واقعی FCM/Apple، PostgreSQL تولید و Build نهایی React باید در محیط تست سازمان بررسی شوند.

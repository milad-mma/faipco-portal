# گزارش تردد ماهانه

قابلیتی کاملاً مستقل از سیستم آزمایشی «ثبت ورود/خروج با GPS» — این یکی
مستقیماً از دستگاه‌های واقعی حضور و غیاب کارخانه می‌خواند، از همان SQL
Server هر سایت که برای Sync پرسنل هم استفاده می‌شود.

## نکات کلیدی طراحی

- **داده خام، بدون هیچ پردازش اضافه**: طبق درخواست صریح، این گزارش
  دقیقاً همان چیزی را نشان می‌دهد که در دیتابیس ثبت شده — گروه‌بندی
  فقط بر اساس همان ستون تاریخ خام دستگاه است، بدون هیچ تلاشی برای
  «حدس‌زدن» یا «ترکیب‌کردن» ترددهای نزدیک نیمه‌شب بین دو روز. هیچ منطق
  پنهانی روی داده اعمال نمی‌شود.
- **بدون «ورود/خروج»**: چون بدون دانستن برنامه دقیق شیفت هر نفر
  نمی‌شود با اطمینان گفت کدام رکورد ورود و کدام خروج بوده، هر تردد فقط
  با شماره ترتیبی («تردد ۱»، «تردد ۲»، ...) در همان روزی که در دیتابیس
  ثبت شده نمایش داده می‌شود.
- **بدون Permission**: هر پرسنلی خودکار دسترسی دارد، مشروط به این‌که
  برای سایت خودش یک نگاشت (Mapping) تردد تنظیم شده باشد.
- **بدون نام خاص نرم‌افزار در کد**: کاملاً عمومی است؛ برای هر نرم‌افزاری
  که رکورد خام ورود/خروج را در یک جدول SQL Server ذخیره می‌کند کار
  می‌کند — نام جدول/ستون‌ها از یک Mapping قابل‌تنظیم می‌آیند، نه هاردکد.
- **جایگزینی کامل کارت‌های داشبورد**: کارت‌های «گزارش تردد» و «تردد
  امروز» قبلاً به سیستم آزمایشی GPS وصل بودند؛ حالا کاملاً با این منبع
  جدید (`has_monthly_attendance`) جایگزین شدند — سیستم GPS دست‌نخورده
  باقی ماند (صفحه `/attendance-clock`).
- **امنیت**: کد پرسنلی همیشه از `Employee` کاربر لاگین‌شده (سشن) خوانده
  می‌شود. کوئری SQL، مقادیر را همیشه Parameterized می‌فرستد.

## نحوه اتصال به دیتابیس — زنده، بدون ذخیره‌سازی

این بخش کاملاً مستقل از Sync Engine (همگام‌سازی خودکار پرسنل) است، با
این‌که از همان اتصال دیتابیس سایت (`SiteConnection`) استفاده می‌کند:

| | Sync Engine (همگام‌سازی پرسنل) | گزارش تردد ماهانه |
|---|---|---|
| چه زمانی اجرا می‌شود | دوره‌ای/زمان‌بندی‌شده (طبق تنظیمات Sync هر سایت) | فقط وقتی کاربر گزارش را باز می‌کند یا ماه را عوض می‌کند |
| داده کجا می‌رود | در دیتابیس خودِ پرتال (PostgreSQL) ذخیره/Upsert می‌شود | هیچ‌جا ذخیره نمی‌شود — مستقیماً از SQL Server خوانده و بلافاصله به مرورگر کاربر نمایش داده می‌شود |
| جدول مقصد | `employees` (دیتابیس خودِ پرتال) | — (بدون جدول مقصد؛ فقط پاسخ API) |

یعنی هر بار که کاربر صفحه «گزارش تردد ماهانه» را باز می‌کند (یا ماه را
تغییر می‌دهد)، یک اتصال SQL Server تازه به دیتابیس همان سایت برقرار
می‌شود، کوئری اجرا می‌شود، و نتیجه مستقیماً برگردانده می‌شود — بدون
هیچ Cache یا ذخیره‌سازی میانی. دفعه بعد که همان گزارش باز شود، دوباره
از صفر از دیتابیس خوانده می‌شود.

## معماری Backend

### نگاشت سطح Site — دقیقاً هم‌الگو با نگاشت پرسنل

`AttendanceMapping` (Migration 038) — دقیقاً همان الگوی `EmployeeMapping`
موجود (که برای Sync پرسنل استفاده می‌شود): چون نرم‌افزارهای مختلف حضور و
غیاب دستگاهی نام جدول/ستون متفاوتی دارند، این‌ها هاردکد نیستند، بلکه از
پنل «تنظیمات سایت» → تب «نگاشت تردد» قابل‌تنظیم‌اند:

| فیلد | توضیح |
|---|---|
| `table_name` | نام جدولی که رکورد خام ورود/خروج در آن ذخیره می‌شود |
| `personnel_code_column` | نام ستون کد پرسنلی |
| `date_column` | نام ستون تاریخ (فرمت عددی شمسی فشرده، مثل `14050524`) |
| `time_column` | نام ستون ساعت (فرمت عددی فشرده، مثل `618` یا `1401`) |

وجود یا نبود این رکورد برای یک Site، خودِ «آیا گزارش تردد ماهانه برای
این سایت فعال است؟» را هم مشخص می‌کند. فقط برای Siteی با اتصال از نوع
SQL Server قابل‌تنظیم است.

### سرویس کوئری (`monthly_attendance_service.py`)

مستقل از Sync Engine (که یک `MSSQLAdapter` جداگانه با کاربرد «کل جدول را
بگیر» دارد) — یک اتصال `pymssql` اختصاصی، با نام جدول/ستون‌ها به‌صورت
داینامیک از `AttendanceMapping`:

```sql
SELECT [{date_column}], [{time_column}]
FROM [{table_name}]
WHERE [{personnel_code_column}] = %(emp_no)s
  AND [{date_column}] BETWEEN %(from_date)s AND %(to_date)s
ORDER BY [{date_column}] ASC, [{time_column}] ASC
```

نام جدول/ستون (فقط از تنظیمات Admin با مجوز `sites.manage`) با
`[براکت]` کوته می‌شوند — همان الگوی Sync Engine
(`app/sync_engine/adapters/mssql_adapter.py`). مقادیر واقعی
(`emp_no`/`from_date`/`to_date`) همیشه Parameterized هستند.

نتیجه کوئری دقیقاً بر اساس همان ستون `date_column` خام گروه‌بندی
می‌شود — بدون هیچ تغییر یا ترکیب. برای هر روز، فهرست همه زمان‌های
ثبت‌شده در دیتابیس، به همان ترتیبی که ثبت شده‌اند.

### توابع تاریخ شمسی (`app/core/persian_date.py`)

- `jalali_days_in_month(year, month)`: تعداد واقعی روزهای یک ماه شمسی
  (شامل تشخیص کبیسه اسفند).
- `jalali_year_month_to_yyyymmdd_range(year, month)`: `(FromDate, ToDate)`
  به فرمت عددی `YYYYMMDD`.

هر دو با تبدیل به میلادی و `timedelta` استاندارد پایتون (نه محاسبه شمسی
دستی) کار می‌کنند، برای اطمینان کامل از صحت.

### Endpoint (`GET /monthly-attendance/report`)

کاملاً در یک Router جدا (`endpoints/monthly_attendance.py`). `year`/`month`
اختیاری — بدونشان، ماه شمسی جاری پیش‌فرض است. اگر سایت کاربر
`AttendanceMapping` نداشته باشد یا اتصال دیتابیس تعریف نشده باشد، ۴۰۴
می‌دهد.

### `has_monthly_attendance` در `/auth/me`

از همان Query موجودی که `site_name`/`department_name` را هم می‌گیرد (با
یک `LEFT JOIN` اضافه به `AttendanceMapping`) — یک فلگ ساده (نه Permission)
در `UserOut`؛ `True` یعنی برای سایت این پرسنل یک نگاشت تردد تنظیم شده است.

## Frontend

- **`MonthlyAttendanceReportPage.jsx`** (مسیر `/monthly-attendance`):
  جدول با ستون‌های «تردد N» کاملاً پویا (بر اساس `max_transits_in_month`)
  + `JalaliMonthYearFilter` (کامپوننت مشترک، همان الگوی گزارش ورود/خروج GPS).
- کارت «تردد امروز» در داشبورد: روز جاری شمسی را (با `gregorianToJalali`
  از `utils/jalaliDate.js`) در آرایه `days` گزارش پیدا می‌کند و
  «اولین تردد»/«آخرین تردد» همان روز را نشان می‌دهد.
- **`SiteSettingsPage.jsx`** → تب «نگاشت تردد»: فرم ۴ فیلدی (نام جدول +
  ۳ نام ستون)، دقیقاً هم‌الگو با تب «Mapping ستون‌ها» موجود برای پرسنل —
  فقط برای اتصال از نوع SQL Server فعال است.

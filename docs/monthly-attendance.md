# گزارش تردد ماهانه

قابلیتی کاملاً مستقل از سیستم آزمایشی «ثبت ورود/خروج با GPS» — این یکی
مستقیماً از دستگاه‌های واقعی حضور و غیاب کارخانه می‌خواند، از همان SQL
Server هر سایت که برای Sync پرسنل هم استفاده می‌شود.

## نکات کلیدی طراحی

- **داده خام، بدون هیچ پردازش اضافه**: طبق درخواست صریح، این گزارش
  دقیقاً همان چیزی را نشان می‌دهد که در دیتابیس ثبت شده — گروه‌بندی
  فقط بر اساس همان ستون تاریخ خام دستگاه است، بدون هیچ تلاشی برای
  «حدس‌زدن» یا «ترکیب‌کردن» ترددهای نزدیک نیمه‌شب بین دو روز. هیچ منطق
  پنهانی روی داده اعمال نمی‌شود.
- **بدون «ورود/خروج»**: چون بدون دانستن برنامه دقیق شیفت هر نفر
  نمی‌شود با اطمینان گفت کدام رکورد ورود و کدام خروج بوده، هر تردد فقط
  با شماره ترتیبی («تردد ۱»، «تردد ۲»، ...) در همان روزی که در دیتابیس
  ثبت شده نمایش داده می‌شود.
- **بدون Permission**: هر پرسنلی خودکار دسترسی دارد، مشروط به این‌که
  برای سایت خودش یک نگاشت (Mapping) تردد تنظیم شده باشد.
- **بدون نام خاص نرم‌افزار در کد**: کاملاً عمومی است؛ برای هر نرم‌افزاری
  که رکورد خام ورود/خروج را در یک جدول SQL Server ذخیره می‌کند کار
  می‌کند — نام جدول/ستون‌ها از یک Mapping قابل‌تنظیم می‌آیند، نه هاردکد.
- **جایگزینی کامل کارت‌های داشبورد**: کارت‌های «گزارش تردد» و «تردد
  امروز» قبلاً به سیستم آزمایشی GPS وصل بودند؛ حالا کاملاً با این منبع
  جدید (`has_monthly_attendance`) جایگزین شدند — سیستم GPS دست‌نخورده
  باقی ماند (صفحه `/attendance-clock`).
- **امنیت**: کد پرسنلی همیشه از `Employee` کاربر لاگین‌شده (سشن) خوانده
  می‌شود. کوئری SQL، مقادیر را همیشه Parameterized می‌فرستد.

## نحوه اتصال به دیتابیس — زنده، بدون ذخیره‌سازی

این بخش کاملاً مستقل از Sync Engine (همگام‌سازی خودکار پرسنل) است، با
این‌که از همان اتصال دیتابیس سایت (`SiteConnection`) استفاده می‌کند:

| | Sync Engine (همگام‌سازی پرسنل) | گزارش تردد ماهانه |
|---|---|---|
| چه زمانی اجرا می‌شود | دوره‌ای/زمان‌بندی‌شده (طبق تنظیمات Sync هر سایت) | فقط وقتی کاربر گزارش را باز می‌کند یا ماه را عوض می‌کند |
| داده کجا می‌رود | در دیتابیس خودِ پرتال (PostgreSQL) ذخیره/Upsert می‌شود | هیچ‌جا ذخیره نمی‌شود — مستقیماً از SQL Server خوانده و بلافاصله به مرورگر کاربر نمایش داده می‌شود |
| جدول مقصد | `employees` (دیتابیس خودِ پرتال) | — (بدون جدول مقصد؛ فقط پاسخ API) |

یعنی هر بار که کاربر صفحه «گزارش تردد ماهانه» را باز می‌کند (یا ماه را
تغییر می‌دهد)، یک اتصال SQL Server تازه به دیتابیس همان سایت برقرار
می‌شود، کوئری اجرا می‌شود، و نتیجه مستقیماً برگردانده می‌شود — بدون
هیچ Cache یا ذخیره‌سازی میانی. دفعه بعد که همان گزارش باز شود، دوباره
از صفر از دیتابیس خوانده می‌شود.

## معماری Backend

### نگاشت سطح Site — دقیقاً هم‌الگو با نگاشت پرسنل

`AttendanceMapping` (Migration 038) — دقیقاً همان الگوی `EmployeeMapping`
موجود (که برای Sync پرسنل استفاده می‌شود): چون نرم‌افزارهای مختلف حضور و
غیاب دستگاهی نام جدول/ستون متفاوتی دارند، این‌ها هاردکد نیستند، بلکه از
پنل «تنظیمات سایت» → تب «نگاشت تردد» قابل‌تنظیم‌اند:

| فیلد | توضیح |
|---|---|
| `table_name` | نام جدولی که رکورد خام ورود/خروج در آن ذخیره می‌شود |
| `personnel_code_column` | نام ستون کد پرسنلی |
| `date_column` | نام ستون تاریخ (فرمت عددی شمسی فشرده، مثل `14050524`) |
| `time_column` | نام ستون ساعت (فرمت عددی فشرده، مثل `618` یا `1401`) |

وجود یا نبود این رکورد برای یک Site، خودِ «آیا گزارش تردد ماهانه برای
این سایت فعال است؟» را هم مشخص می‌کند. فقط برای Siteی با اتصال از نوع
SQL Server قابل‌تنظیم است.

### سرویس کوئری (`monthly_attendance_service.py`)

مستقل از Sync Engine (که یک `MSSQLAdapter` جداگانه با کاربرد «کل جدول را
بگیر» دارد) — یک اتصال `pymssql` اختصاصی، با نام جدول/ستون‌ها به‌صورت
داینامیک از `AttendanceMapping`:

```sql
SELECT [{date_column}], [{time_column}]
FROM [{table_name}]
WHERE [{personnel_code_column}] = %(emp_no)s
  AND [{date_column}] BETWEEN %(from_date)s AND %(to_date)s
ORDER BY [{date_column}] ASC, [{time_column}] ASC
```

نام جدول/ستون (فقط از تنظیمات Admin با مجوز `sites.manage`) با
`[براکت]` کوته می‌شوند — همان الگوی Sync Engine
(`app/sync_engine/adapters/mssql_adapter.py`). مقادیر واقعی
(`emp_no`/`from_date`/`to_date`) همیشه Parameterized هستند.

نتیجه کوئری دقیقاً بر اساس همان ستون `date_column` خام گروه‌بندی
می‌شود — بدون هیچ تغییر یا ترکیب. برای هر روز، فهرست همه زمان‌های
ثبت‌شده در دیتابیس، به همان ترتیبی که ثبت شده‌اند.

### توابع تاریخ شمسی (`app/core/persian_date.py`)

- `jalali_days_in_month(year, month)`: تعداد واقعی روزهای یک ماه شمسی
  (شامل تشخیص کبیسه اسفند).
- `jalali_year_month_to_yyyymmdd_range(year, month)`: `(FromDate, ToDate)`
  به فرمت عددی `YYYYMMDD`.

هر دو با تبدیل به میلادی و `timedelta` استاندارد پایتون (نه محاسبه شمسی
دستی) کار می‌کنند، برای اطمینان کامل از صحت.

### Endpoint (`GET /monthly-attendance/report`)

کاملاً در یک Router جدا (`endpoints/monthly_attendance.py`). `year`/`month`
اختیاری — بدونشان، ماه شمسی جاری پیش‌فرض است. اگر سایت کاربر
`AttendanceMapping` نداشته باشد یا اتصال دیتابیس تعریف نشده باشد، ۴۰۴
می‌دهد.

### `has_monthly_attendance` در `/auth/me`

از همان Query موجودی که `site_name`/`department_name` را هم می‌گیرد (با
یک `LEFT JOIN` اضافه به `AttendanceMapping`) — یک فلگ ساده (نه Permission)
در `UserOut`؛ `True` یعنی برای سایت این پرسنل یک نگاشت تردد تنظیم شده است.

## Frontend

- **`MonthlyAttendanceReportPage.jsx`** (مسیر `/monthly-attendance`):
  جدول با ستون‌های «تردد N» کاملاً پویا (بر اساس `max_transits_in_month`)
  + `JalaliMonthYearFilter` (کامپوننت مشترک، همان الگوی گزارش ورود/خروج GPS).
- کارت «تردد امروز» در داشبورد: روز جاری شمسی را (با `gregorianToJalali`
  از `utils/jalaliDate.js`) در آرایه `days` گزارش پیدا می‌کند و
  «اولین تردد»/«آخرین تردد» همان روز را نشان می‌دهد.
- **`SiteSettingsPage.jsx`** → تب «نگاشت تردد»: فرم ۴ فیلدی (نام جدول +
  ۳ نام ستون)، دقیقاً هم‌الگو با تب «Mapping ستون‌ها» موجود برای پرسنل —
  فقط برای اتصال از نوع SQL Server فعال است.

## دور سوم — نمایش تعطیلات (اختیاری)

طبق درخواست، امکان رنگ‌آمیزی روزهای تعطیل در گزارش تردد اضافه شد — با
خواندن از یک جدول تقویم که در همان دیتابیس تردد هر سایت وجود دارد (یک
ردیف به‌ازای هر سال+ماه شمسی، با ستون‌های روز شماره‌گذاری‌شده مثل
`D1` تا `D31` — هرکدام صفر یعنی روز عادی، هر عدد غیرصفر یعنی تعطیل).

### فیلدهای جدید (اختیاری) روی `AttendanceMapping` — Migration 039

| فیلد | توضیح |
|---|---|
| `calendar_table_name` | نام جدول تقویم (مثلاً `Calen`) |
| `calendar_year_column` | ستون سال شمسی |
| `calendar_month_column` | ستون شماره ماه شمسی (۱ تا ۱۲) |
| `calendar_day_column_prefix` | پیشوند ستون‌های روز (مثلاً `"D"` برای D1...D31) |

**کاملاً اختیاری** — اگر `calendar_table_name` (یا هرکدام از این چهار
فیلد) خالی باشد، گزارش دقیقاً مثل قبل کار می‌کند، بدون رنگ‌آمیزی
تعطیلات (نه خطا). همچنین اگر خودِ کوئری تقویم با خطا مواجه شود (مثلاً
نام جدول اشتباه)، فقط رنگ‌آمیزی نادیده گرفته می‌شود — کل گزارش تردد
خراب نمی‌شود.

### کوئری

```sql
SELECT [D1], [D2], ..., [D31]
FROM [{calendar_table_name}]
WHERE [{calendar_year_column}] = %(year)s AND [{calendar_month_column}] = %(month)s
```

یک ردیف برمی‌گردد؛ هر ستون غیرصفر (طبق داده واقعی: `500` یا `501`) یعنی
آن روز تعطیل است — منطق به‌جای هاردکد این دو عدد خاص، هر مقدار غیرصفر
را تعطیل در نظر می‌گیرد (کلی‌تر و مقاوم‌تر در برابر مقادیر خاص دیگر).

### Frontend

`MonthlyAttendanceReportPage.jsx`: هر روز پاسخ API یک فیلد
`is_holiday: boolean` دارد؛ اگر `true` باشد، آن ردیف جدول با رنگ قرمز
(متن + پس‌زمینه ملایم) نمایش داده می‌شود. `SiteSettingsPage.jsx` → تب
«نگاشت تردد»: بخش «تقویم و تعطیلات (اختیاری)» با چهار فیلد بالا اضافه شد.

## دور چهارم — نمایش روز هفته

طبق درخواست، ستون «روز هفته» (شنبه تا جمعه) به گزارش اضافه شد.

⚠️ برخلاف تصور اولیه، این **نیازی به جدول تقویم (`Calen`) ندارد** — روز
هفته یک واقعیت خالص تقویمی محاسبه‌شده از خودِ تاریخ شمسی است (نه
داده‌ای که در دیتابیس ذخیره شده باشد)، پس همیشه در دسترس است، حتی برای
سایتی که اصلاً نگاشت تقویم/تعطیلات ندارد.

### `jalali_weekday_name` (`app/core/persian_date.py`)

برای جلوگیری از هرگونه ابهام در قرارداد شماره‌گذاری روز هفته خودِ
jdatetime، این تابع تاریخ شمسی را به معادل میلادی تبدیل می‌کند (همان
`togregorian()` اثبات‌شده)، از `weekday()` استاندارد پایتون (دوشنبه=۰
... یکشنبه=۶) استفاده می‌کند، و به نام روز هفته شمسی نگاشت می‌کند.
درستی این نگاشت با یک نقطه مرجع شناخته‌شده (نوروز ۱۴۰۳ برابر با
چهارشنبه) تأیید شد.

هر روز پاسخ API حالا یک فیلد `weekday` (رشته، مثل `"شنبه"`) هم دارد؛
`MonthlyAttendanceReportPage.jsx` آن را در یک ستون جدید نمایش می‌دهد.

## دور پنجم — پشتیبانی از MySQL و PostgreSQL (نه فقط SQL Server)

طبق درخواست، این گزارش دیگر محدود به اتصال از نوع SQL Server نیست -
حالا برای هر سه نوع اتصال پشتیبانی‌شده این پروژه (SQL Server، MySQL،
PostgreSQL) قابل‌استفاده است، دقیقاً بر اساس همان `db_type` که برای
اتصال Sync پرسنل همان سایت تنظیم شده.

### چرا این محدودیت اصلاً وجود داشت

نسخه اولیه مستقیماً از `pymssql` استفاده می‌کرد و نام جدول/ستون‌ها را
همیشه با `[براکت]` (نحو مخصوص SQL Server) کوته می‌کرد - برای MySQL/PostgreSQL
نه تنها درایور اشتباه بود، نحو کوته‌کردن هم نامعتبر می‌بود.

### راه‌حل - همان الگوی چند-دیتابیسی Sync Engine

`monthly_attendance_service.py` سه تابع کمکی جدید گرفت:

- **`_quote(db_type, name)`**: علامت کوته درست را برمی‌گرداند - SQL Server
  `[نام]`، MySQL `` `نام` ``، PostgreSQL `"نام"`.
- **`_connect(conn)`**: بر اساس `conn.db_type`، به درایور درست
  (`pymssql`/`pymysql`/`psycopg2`) دیسپچ می‌کند - دقیقاً همان پارامترهای
  اتصالی که در `app/sync_engine/adapters/` استفاده می‌شود.
- **`_dict_cursor(connection, db_type)`**: چون هر سه درایور روش متفاوتی
  برای گرفتن یک Cursor دیکشنری‌مانند دارند (`as_dict=True`، `cursorclass`
  در لحظه اتصال، یا `cursor_factory` در لحظه ساخت Cursor)، این تابع آن
  تفاوت را یک‌جا مدیریت می‌کند.

⚠️ **نکته مهم درباره PostgreSQL و بزرگی/کوچکی حروف**: نام مستعار ستون‌ها
(`AS ...`) در کوئری اصلی هم عمداً کوته می‌شوند (`AS "AttendanceDate"`)
- چون PostgreSQL نام‌های کوته‌نشده را خودکار کوچک می‌کند، و بدون این
  کوته‌کردن، کلید دیکشنری خروجی (`attendancedate`) با آنچه کد پایتون
  انتظار دارد (`AttendanceDate`) مطابقت نمی‌داشت.

⚠️ **همین منطق برای PostgreSQL یعنی Admin باید نام دقیق حروف کوچک/بزرگ
ستون‌های واقعی جدول را وارد کند** (نه فقط نام تقریبی) - این دقیقاً همان
قراردادی است که Sync Engine هم از قبل برای PostgreSQL دنبال می‌کرد
(`app/sync_engine/adapters/postgresql_adapter.py`).

### تغییرات دیگر

- `site_service.py`: اعتبارسنجی «فقط برای اتصال SQL Server قابل‌تنظیم
  است» حذف شد - الان فقط بررسی می‌شود که اصلاً یک اتصال دیتابیس برای
  این سایت تعریف شده باشد (صرف‌نظر از نوعش).
- `SiteSettingsPage.jsx` → تب «نگاشت تردد»: هشدار «فقط SQL Server» و
  تمام شرط‌های غیرفعال‌سازی فیلدها بر اساس `db_type !== "mssql"` حذف
  شدند - فرم برای هر سه نوع اتصال به‌طور یکسان فعال است.

## دور ششم — پشتیبانی از الگوی «ستون‌های جدای ورود/خروج» (نه فقط یک ستون تاریخ/ساعت)

طبق درخواست صریح: برخی نرم‌افزارهای حضور و غیاب به‌جای یک ردیف-به-ازای-
هر-تردد (الگوی اصلی این پروژه)، از چهار ستون جدا برای ورود/خروج استفاده
می‌کنند - مثلاً `enterdate`/`exitdate` و `entertime`/`exittime` - یک
ردیف یعنی یک نشست کامل (ورود+خروج با هم)، نه یک تردد منفرد.

### `AttendanceMappingMode` (Migration 049)

فیلد جدید `mapping_mode` روی `AttendanceMapping` - دو مقدار:

- **`single_column`** (پیش‌فرض، همان رفتار قبلی): `date_column`/`time_column`
  الزامی‌اند.
- **`enter_exit_columns`**: چهار فیلد جدید الزامی‌اند -
  `enter_date_column`/`enter_time_column`/`exit_date_column`/`exit_time_column`.

`date_column`/`time_column` روی خودِ دیتابیس دیگر Nullable هستند - این
الزام («کدام فیلدها برای کدام حالت لازم‌اند») در Backend
(`schemas/site.py`، با یک `model_validator`) اعمال می‌شود، نه در سطح
دیتابیس.

### نرمال‌سازی - بقیه خط لوله بدون تغییر کار می‌کند

`monthly_attendance_service.py` برای حالت `enter_exit_columns`، هر
ردیف (نشست) را به یک یا دو «تردد منفرد» تبدیل می‌کند
(`_normalize_enter_exit_sessions`) - یکی برای لحظه ورود، و اگر خروج
ثبت شده باشد (ستون‌های خروج NULL نباشند)، یکی هم برای لحظه خروج. خروجی
این نرمال‌سازی دقیقاً هم‌شکل با خروجی حالت `single_column` است
(`{"AttendanceDate": ..., "AttendanceTime": ...}`) - یعنی بقیه خط لوله
(گروه‌بندی بر اساس روز، ساخت `days_out`) کاملاً یکسان برای هر دو حالت
اجرا می‌شود، بدون هیچ شاخه‌بندی اضافه.

⚠️ **نشست باز (کاربر هنوز خروج نزده)**: اگر `exit_date_column`/
`exit_time_column` برای یک ردیف NULL باشند، فقط تردد ورود نمایش داده
می‌شود - نه خطا.

⚠️ **شیفت شب (ورود یک روز، خروج روز بعد)**: چون ورود و خروج به‌طور
مستقل بر اساس تاریخ خودشان به روز درست گروه‌بندی می‌شوند (نه بر اساس
تاریخ نشست)، این حالت به‌درستی مدیریت می‌شود - ورود در روز اول ثبت
می‌شود، خروج در روز دوم.

### کوئری - واکشی نشست‌هایی که ورود یا خروجشان داخل بازه ماه است

```sql
SELECT enter_date_column, enter_time_column, exit_date_column, exit_time_column
FROM table_name
WHERE personnel_code_column = %(emp_no)s
  AND (
        enter_date_column BETWEEN %(from_date)s AND %(to_date)s
        OR exit_date_column BETWEEN %(from_date)s AND %(to_date)s
      )
ORDER BY enter_date_column ASC, enter_time_column ASC
```

شرط `OR` عمداً هر دو تاریخ را چک می‌کند - وگرنه نشستی که مثلاً از آخر
ماه قبل شروع و اول همین ماه تمام شده (یا برعکس) از قلم می‌افتاد.

### Frontend

`SiteSettingsPage.jsx` → تب «نگاشت تردد»: یک انتخابگر «روش نگاشت»
اضافه شد؛ بر اساس انتخاب، یا دو فیلد (تاریخ/ساعت) یا چهار فیلد
(تاریخ/ساعت ورود + تاریخ/ساعت خروج) نمایش داده می‌شود. تعویض روش،
فیلدهای روش قبلی را پاک می‌کند (برای جلوگیری از داده باقی‌مانده
گیج‌کننده در دیتابیس).

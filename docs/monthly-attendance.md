# گزارش تردد ماهانه

قابلیتی کاملاً مستقل از سیستم آزمایشی «ثبت ورود/خروج با GPS» — این یکی
مستقیماً از دستگاه‌های واقعی حضور و غیاب کارخانه می‌خواند، از همان SQL
Server هر سایت که برای Sync پرسنل هم استفاده می‌شود.

## نکات کلیدی طراحی

- **بدون Permission**: طبق درخواست صریح، این گزارش نیاز به هیچ مجوز
  RBAC ندارد — هر پرسنلی خودکار دسترسی دارد، **مشروط به این‌که برای
  سایت خودش یک نگاشت (Mapping) تردد تنظیم شده باشد**.
- **بدون نام خاص نرم‌افزار در کد**: طبق درخواست صریح، این قابلیت به هیچ
  نرم‌افزار حضور و غیاب خاصی (نام تجاری) اشاره نمی‌کند — کاملاً عمومی
  است و برای هر نرم‌افزاری که رکورد خام ورود/خروج را در یک جدول
  SQL Server ذخیره می‌کند کار می‌کند؛ نام جدول/ستون‌ها از یک Mapping
  قابل‌تنظیم می‌آیند، نه هاردکد.
- **جایگزینی کامل کارت‌های داشبورد**: کارت‌های «گزارش تردد» و «تردد
  امروز» در `PersonalDashboardPage.jsx` قبلاً به سیستم آزمایشی GPS
  (`can_clock_in_out`) وصل بودند؛ طبق تصمیم صریح، حالا کاملاً با این
  منبع جدید (`has_monthly_attendance`) جایگزین شدند — سیستم GPS دیگر به
  این دو کارت وصل نیست (ولی خودش، صفحه `/attendance-clock`، دست‌نخورده
  باقی ماند).
- **امنیت**: کد پرسنلی همیشه از `Employee` کاربر لاگین‌شده (سشن) خوانده
  می‌شود — هیچ پارامتر ورودی نمی‌تواند آن را Override کند. کوئری SQL،
  مقادیر را همیشه Parameterized می‌فرستد.

## معماری Backend

### نگاشت سطح Site — دقیقاً هم‌الگو با نگاشت پرسنل

⚠️ **یادداشت تاریخچه Migration**: نسخه اولیه این قابلیت یک فلگ ساده
روشن/خاموش (`sites.kara_workflow_enabled`، Migration 037) بود. طبق
درخواست صریح (حذف کامل هر اشاره‌ای به نام نرم‌افزار خاص + افزودن نگاشت
واقعی جدول/ستون)، این فلگ حذف و با `AttendanceMapping` جایگزین شد —
اما چون Migration 037 از قبل روی برخی دیتابیس‌ها واقعاً اجرا شده بود،
این تغییر در یک Migration *جدید* (038) انجام شد، نه با ویرایش 037؛
هر دو Migration باید به ترتیب اجرا شوند.

`AttendanceMapping` (Migration 038) — دقیقاً همان الگوی `EmployeeMapping`
موجود (که برای Sync پرسنل استفاده می‌شود): چون نرم‌افزارهای مختلف حضور و
غیاب دستگاهی نام جدول/ستون متفاوتی دارند، این‌ها هاردکد نیستند، بلکه از
پنل «تنظیمات سایت» → تب «نگاشت تردد» قابل‌تنظیم‌اند:

| فیلد | توضیح |
|---|---|
| `table_name` | نام جدولی که رکورد خام ورود/خروج در آن ذخیره می‌شود |
| `personnel_code_column` | نام ستون کد پرسنلی |
| `date_column` | نام ستون تاریخ (فرمت عددی شمسی فشرده، مثل `14050524`) |
| `time_column` | نام ستون ساعت (فرمت عددی فشرده، مثل `618` یا `1401`) |

**وجود یا نبود** این رکورد برای یک Site، خودِ «آیا گزارش تردد ماهانه
برای این سایت فعال است؟» را هم مشخص می‌کند — یک فلگ boolean جدا لازم
نیست. فقط برای Siteی با اتصال از نوع SQL Server قابل‌تنظیم است.

### سرویس کوئری (`monthly_attendance_service.py`)

مستقل از Sync Engine (که برای «کل جدول را بگیر» طراحی شده) — یک اتصال
`pymssql` اختصاصی، با نام جدول/ستون‌ها به‌صورت داینامیک از
`AttendanceMapping` (نه هاردکد):

```sql
SELECT [{date_column}], [{time_column}],
       ROW_NUMBER() OVER (PARTITION BY [{date_column}] ORDER BY [{time_column}]) AS Seq
FROM [{table_name}]
WHERE [{personnel_code_column}] = %(emp_no)s
  AND [{date_column}] BETWEEN %(from_date)s AND %(to_date)s
```

نام جدول/ستون (که فقط از تنظیمات Admin با مجوز `sites.manage` می‌آیند)
با `[براکت]` کوته می‌شوند — SQL Server اجازه Parameterized-کردن نام
جدول/ستون را نمی‌دهد، فقط مقادیر؛ همان الگوی استفاده‌شده در Sync Engine
(`app/sync_engine/adapters/mssql_adapter.py`) برای همین نوع نیاز. مقادیر
واقعی (`emp_no`/`from_date`/`to_date`) همیشه Parameterized هستند —
همان چیزی که واقعاً جلوی SQL Injection را می‌گیرد.

منطق ورود/خروج کاملاً بر اساس ترتیب زمانی (`Seq` فرد=ورود، زوج=خروج) —
نه یک ستون «جهت» مشخص (که در داده‌های دستگاهی معمولاً معنای قابل‌اعتمادی ندارد).

### توابع تاریخ شمسی جدید (`app/core/persian_date.py`)

- `jalali_days_in_month(year, month)`: تعداد واقعی روزهای یک ماه شمسی
  (شامل تشخیص کبیسه اسفند) — با تبدیل به میلادی و `timedelta` استاندارد
  پایتون (نه محاسبه دستی/هاردکد)، برای اطمینان کامل از صحت.
- `jalali_year_month_to_yyyymmdd_range(year, month)`: `(FromDate, ToDate)`
  به فرمت عددی `YYYYMMDD`.

### Endpoint (`GET /monthly-attendance/report`)

- کاملاً در یک Router جدا (`endpoints/monthly_attendance.py`) — نه در
  `endpoints/attendance.py` (که مخصوص سیستم GPS است).
- `year`/`month` اختیاری — بدونشان، ماه شمسی جاری پیش‌فرض است.
- اگر سایت کاربر `AttendanceMapping` نداشته باشد یا اتصال دیتابیس تعریف
  نشده باشد، ۴۰۴ می‌دهد (نه تلاش برای اتصال و شکست با خطای خام).

### `has_monthly_attendance` در `/auth/me`

از همان Query موجودی که `site_name`/`department_name` را هم می‌گیرد
(با یک `LEFT JOIN` اضافه به `AttendanceMapping`، بدون Query جداگانه) —
به‌عنوان یک فلگ ساده (نه Permission) در `UserOut` قرار می‌گیرد؛ `True`
یعنی برای سایت این پرسنل یک نگاشت تردد تنظیم شده است.

## Frontend

- **`MonthlyAttendanceReportPage.jsx`** (مسیر `/monthly-attendance`):
  جدول با ستون‌های ورود/خروج کاملاً پویا (بر اساس `max_pairs_in_month`)
  + `JalaliMonthYearFilter` (کامپوننت مشترک، همان الگوی گزارش ورود/خروج GPS).
- کارت «تردد امروز» در داشبورد: روز جاری شمسی را (با `gregorianToJalali`
  از `utils/jalaliDate.js` — همان تابع تبدیل تاریخ محلی موجود در پروژه،
  بدون کتابخانه خارجی) در آرایه `days` گزارش پیدا می‌کند و اولین
  ورود/آخرین خروج همان روز را نشان می‌دهد.
- **`SiteSettingsPage.jsx`** → تب «نگاشت تردد»: فرم ۴ فیلدی (نام جدول +
  ۳ نام ستون)، دقیقاً هم‌الگو با تب «Mapping ستون‌ها» موجود برای پرسنل —
  فقط برای اتصال از نوع SQL Server فعال است.

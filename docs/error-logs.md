# گزارش خطاها (Migration 105)

هدف: مدیر بدون SSH و `journalctl` ببیند پرتال کجا خطا داده، چند بار، برای چه کسی و چرا.
صفحه: **پنل مدیریت ← گزارش خطاها** (`/error-logs`)، مجوز `system.logs`.

## چه چیزهایی ثبت می‌شود
| نوع (`kind`) | منبع | مثال |
|---|---|---|
| `error` خطای سرور | هر `logger.error` / `logger.exception` در بک‌اند + هر خطای پیش‌بینی‌نشده‌ی Endpoint | `Invalid column name 'BranchCode'` در نگاشت مرخصی |
| `slow` درخواست کند | هر درخواست API بیش از **۳ ثانیه** (`SLOW_REQUEST_SECONDS`) | `GET /api/v1/sites` در ۸.۲ ثانیه |
| `client` خطای مرورگر | خطای JavaScript، صفحه‌ی سفید (`AppErrorBoundary`)، درخواستی که اصلاً به سرور نرسید | `Failed to fetch` روی صفحه‌ی سایت‌ها |
| `android` خطای اپ | بخش بومی اپ اندروید (کرش، ثبت محدوده‌ها، کارهای پس‌زمینه) — **فقط وقتی قابلیت اپ روشن است** | `crash:main: NullPointerException` |

قطعی شبکه‌ی درخواست‌های پس‌زمینه (نسخه، برندینگ، وضعیت کپچا، اعلان تغییرات، شمارنده‌ی پیام‌ها، وضعیت اپ، پرسش‌های
دوره‌ای وضعیت آپدیت/بازیابی؛ `BACKGROUND_PATHS` در `api/client.js`) ثبت نمی‌شود، و قطعی هم‌زمانِ چند درخواست یک صفحه
یک گزارش است (تا یک دقیقه). پس «ارتباط مرورگر با سرور» فقط قطعی‌هایی را نشان می‌دهد که کاربر با آن به مشکل خورده.
قاعده: تک‌کاربره = اینترنت همان کاربر؛ چند کاربر در یک بازه = سرور، Reverse Proxy یا شبکه.

بعد از هر آپدیت، تب‌های باز قدیمی فایل‌های جدید را پیدا نمی‌کنند (ChunkLoadError): این خطا ثبت نمی‌شود و صفحه یک‌بار
خودکار رفرش می‌شود. درخواستی که با رفتن از صفحه یا رفتن اپ به پس‌زمینه قطع شود هم ثبت نمی‌شود.

مسیرهای طولانی ذاتی (بکاپ، بازیابی، آپدیت، دانلود APK، دکمه‌های «آزمایش» ایمیل/پیامک/SMB/FTP/اتصال کاراوب، و ارسال دوباره‌ی Push) در «درخواست کند» شمرده نمی‌شوند (`_SLOW_EXEMPT` در `main.py`).

## گروه‌بندی و کد پیگیری
- خطاهای یکسان (همان نوع، بخش و متن بدون اعداد) یک **گروه** هستند: تعداد، اولین و آخرین زمان (`error_logs`).
- هر رخداد جدا هم در `error_log_occurrences` با **کد پیگیری** ۶ حرفی (مثل `A3F09C`)، کاربر، IP و مسیر ثبت می‌شود.
- هر پاسخ API هدر `X-Request-ID` دارد؛ پیام خطای ۵۰۰ هم کد را نشان می‌دهد: «خطای داخلی سرور رخ داد. کد پیگیری: A3F09C».
  کاربر همین کد را می‌فرستد و مدیر در جست‌وجوی صفحه وارد می‌کند. لاگ Nginx هم کد را دارد (`rid=`).
- **بخش** (`category`) خودکار از نام ماژول و متن خطا: کاراوب، همگام‌سازی، ایمیل، پیامک، بکاپ، حضور، مرخصی، ... .
- برای خطاهای رایج یک **راهنمای فارسی** کنار خطا نشان داده می‌شود (`hint_for`)؛ مثلاً ستون نامعتبر کاراوب ←
  «نگاشت‌های سایت را بررسی کنید».

## «حل شد»
دکمه‌ی «حل شد» گروه را می‌بندد. اگر همان خطا دوباره رخ دهد، گروه **خودکار باز** می‌شود (و ایمیل هشدار می‌رود).

## هشدار ایمیلی
- در کارت «هشدار ایمیلی» همین صفحه: روشن/خاموش و تا ۱۰ گیرنده (`system_settings`، کلید `error_alert_settings`).
- **فقط وقتی SMTP در «تنظیمات سامانه ← ایمیل» فعال و کامل است** فرستاده می‌شود؛ وگرنه هیچ ایمیلی نمی‌رود و صفحه
  پیام «ایمیل تنظیم نشده» نشان می‌دهد.
- فقط برای گروه **جدید** یا گروه حل‌شده‌ای که **دوباره** رخ داده؛ تکرار یک خطای باز ایمیل نمی‌شود.
  درخواست کند ایمیل نمی‌شود. سقف ۱۰ ایمیل در ساعت.
- دکمه‌ی «ایمیل آزمایشی».

## کارایی و امنیت
- ثبت هیچ‌وقت درخواست کاربر را کند نمی‌کند: رکورد در صف حافظه می‌رود و هر ۳ ثانیه یک Task جدا در دیتابیس می‌نویسد
  (`DbErrorHandler` روی logger ریشه، `flush`).
- رمز، توکن، JWT، هدر Authorization و رمز داخل آدرس اتصال پیش از ذخیره حذف می‌شوند (`redact`)؛ مقادیر پارامترهای
  کوئری هم در متن خطاهای دیتابیس چاپ نمی‌شوند (`hide_parameters` در `db/session.py`، به‌جز حالت DEBUG).
- نوشتن ناموفق (قطعی دیتابیس) رخدادها را دور نمی‌ریزد؛ به صف برمی‌گردند (حداکثر ۳ تلاش). دو Worker با ترتیب ثابت
  می‌نویسند (بدون بن‌بست) و رخداد قدیمی‌تر «آخرین رخداد» یا وضعیت «حل شد» را عوض نمی‌کند.
- `POST /error-logs/client` بدون ورود کار می‌کند (صفحه‌ی ورود هم خطا گزارش کند)؛ سقف ۳۰ گزارش در دقیقه برای هر IP.
- نگهداری **۳۰ روز**؛ پاک‌سازی روزانه ساعت ۳:۲۰ (`_error_logs_cleanup_job`).
- لاگ‌ها همچنان در `journalctl -u faipco-backend` هم هستند.

## اپ اندروید
`Diag.kt`: کرش اپ (`installCrashHandler`)، خطا در `GeofenceReceiver` / `ConnectivityReceiver`، ثبت محدوده‌ها
(`GeofenceController.apply`، به‌جز نبود دسترسی)، `Online.update` و خطاهای پیش‌بینی‌نشده‌ی Workerها. در صف گوشی
(حداکثر ۵۰؛ کرش با commit هم‌زمان پیش از بسته شدن) و با اینترنت به `POST /mobile/device/errors`. هر خطای یکسان در ۱۰
دقیقه یک‌بار. قابلیت خاموش یا گوشی بدون اتصال ← هیچ چیز فرستاده نمی‌شود.

## Nginx
`install.sh` قالب لاگ `faipco_timed` را اضافه می‌کند: `rid=` کد پیگیری، `urt=` زمان بک‌اند، `rt=` کل زمان پاسخ.
اگر `rt` بزرگ و `urt` کوچک باشد، کندی بیرون از بک‌اند است (شبکه، Reverse Proxy):
```bash
sudo grep -E 'rt=([3-9]|[1-9][0-9])\.' /var/log/nginx/access.log | tail
```

## API
| مسیر | توضیح |
|---|---|
| `GET /error-logs` | فهرست (فیلتر `kind`، `category`، `state`، `q` شامل کد پیگیری، `since_hours`) + خلاصه‌ی ۲۴ ساعت |
| `GET /error-logs/{id}` | جزئیات + Traceback + ۵۰ رخداد آخر |
| `POST /error-logs/{id}/resolve` ، `/reopen` | حل شد / باز کردن |
| `POST /error-logs/resolve-all` | همه‌ی باز‌ها (با فیلتر نوع/بخش) |
| `GET/PUT /error-logs/settings` ، `POST /settings/test` | هشدار ایمیلی |
| `POST /error-logs/client` | گزارش مرورگر (بدون ورود) |
| `POST /mobile/device/errors` | گزارش اپ اندروید (توکن گوشی) |

## تشخیص: «مشکل از کجاست و حالا چه کنم»

هر گروه خطا یک تشخیص دارد (`app/services/error_diagnosis.py`، تابع خالص `diagnose`) که روی صفحه به‌صورت کادر رنگی
«مشکل از: … / کار شما: …» نشان داده می‌شود:

| برچسب | سطح | یعنی |
|---|---|---|
| اینترنت همان کاربر | 🟢 ok | قطعی شبکه‌ی مرورگر، کمتر از ۳ کاربر (IP) متفاوت در ±۱۵ دقیقه |
| سرور یا شبکه (چند کاربر) | 🔴 critical | همان قطعی برای ۳ کاربر یا بیشتر هم‌زمان |
| داده‌ی نامعتبر یک پرسنل | 🟠 warn | value too long / out of range / تبدیل ناموفق — معمولاً داده‌ی کاراوب |
| اتصال یا تنظیمات کاراوب | 🟠 warn | ستون/جدول اشتباه در نگاشت، ورود ناموفق یا در دسترس نبودن SQL Server |
| تنظیمات ایمیل/پیامک/بکاپ/اعلان | 🟠 warn | خطای سرور در همان بخش |
| کندی کاراوب | 🟠 warn | درخواست کند در بخش‌های وابسته به کاراوب (تردد، مرخصی، همگام‌سازی…) |
| سرور پرتال کند است | 🔴 critical | همان درخواست ۵ بار یا بیشتر در ۲۴ ساعت کند |
| کندی گذرا / نسخه‌ی قدیمی مرورگر | 🟢 ok | تک‌کندی، یا ChunkLoadError بعد از آپدیت |
| باگ پرتال (خطای سرور / صفحه‌ی سفید) | 🔴 critical | خطای پیش‌بینی‌نشده‌ی Endpoint، خطای JavaScript |
| باگ اپ اندروید | 🔴 critical | خطای بخش بومی اپ |
| نامشخص | ⚪ unknown | قاعده‌ای نخورد — برای پشتیبانی بفرستید |

- **تب پیش‌فرض «نیاز به اقدام»** (warn / critical / unknown) با شمارنده؛ «کاری لازم نیست» جدا. بالای صفحه: «N مورد
  نیاز به اقدام دارد» یا «پرتال سالم است».
- **حل خودکار:** موارد «کاری لازم نیست» که ۲۴ ساعت رخداد تازه نداشته‌اند هر ساعت خودکار «حل شد» می‌شوند
  (`auto_resolve_quiet`، Job ساعتی). اگر همان قطعی برای چند نفر رخ دهد، تشخیص خودکار قرمز می‌شود.
- **ایمیل هشدار** فقط برای موارد «نیاز به اقدام».
- **API:** هر آیتم `diagnosis: {key, level, title, action, subject}`؛ `GET /error-logs?attention=action|ok`؛ پاسخ فهرست
  `attention: {action, ok}`؛ `POST /error-logs/resolve-all?attention=...` فقط همان دسته.
- **افزودن قاعده:** هر خطای «نامشخص» که علتش معلوم شد، یک الگو در `error_diagnosis.py` و یک تست در
  `tests/test_error_diagnosis.py` (با نمونه‌ی واقعی) اضافه می‌شود.

# فراموشی رمز عبور از طریق پیامک (ippanel Edge API)

گسترش قابلیت موجود «فراموشی رمز عبور» (`docs/smtp-and-password-reset.md`)
با یک کانال دوم، در کنار ایمیل - کاربر می‌تواند از هرکدام استفاده کند.

## تفاوت اساسی با کانال ایمیل

ایمیل یک لینک قابل‌کلیک می‌فرستد (توکن طولانی و امن در querystring)؛
پیامک یک کد ۶ رقمی می‌فرستد که کاربر باید دستی وارد کند. به همین دلیل،
تجربه کاربری کانال پیامک هم فرق دارد: بعد از درخواست موفق، همان صفحه
(`ForgotPasswordPage.jsx`) یک فرم «کد + رمز عبور جدید» نمایش می‌دهد -
نه فقط پیام «صندوق خود را بررسی کنید».

## تنظیمات پیامک (`SmsSettings`، Migration 048)

یک ردیف Singleton، دقیقاً هم‌الگو با `SmtpSettings`. API Key هرگز خام
ذخیره نمی‌شود (رمزنگاری‌شده) و هرگز در پاسخ API برنمی‌گردد.

### دو روش ارسال (طبق [مستندات ippanel](https://ippanelcom.github.io/Edge-Document/docs/send/))

- **Pattern (توصیه‌شده)**: یک الگوی از پیش در پنل ippanel ساخته و
  تأییدشده (مثلاً «کد تأیید شما: #code#») - شانس بلاک‌شدن پیامک به‌عنوان
  اسپم/تبلیغات کمتر است (رایج برای پیامک‌های تراکنشی/OTP در ایران).
- **Webservice**: متن پیام کاملاً آزاد، با جای‌گذار `{code}`.

### `app/services/sms_service.py`

`send_sms_code()` - از `httpx` (Async، نیازی به `asyncio.to_thread` ندارد،
برخلاف smtplib/pymssql) برای فراخوانی `POST https://edge.ippanel.com/v1/api/send`
استفاده می‌کند. شماره موبایل از فرمت داخلی این پروژه (`09123456789`) به
فرمت مورد نیاز ippanel (E.164، `+989123456789`) تبدیل می‌شود.

## کد تأیید — بدون صفر ابتدایی (نکته مهم)

کد بین `100000` تا `999999` تولید می‌شود (نه `000000` تا `999999`) -
عمداً، چون پارامتر `code` در الگوهای (Pattern) سرویس پیامک معمولاً از
نوع عددی (Integer) تعریف می‌شود؛ یک رشته با صفر ابتدایی (مثل `"003456"`)
در تبدیل به عدد صفرهای ابتدایی‌اش را از دست می‌داد و کد واقعی متفاوت با
چیزی می‌شد که به کاربر پیامک شده بود.

## محافظت در برابر Brute-force

کد ۶ رقمی فقط یک میلیون حالت ممکن دارد - برخلاف توکن ایمیل (یک رشته
تصادفی ۳۲ بایتی، عملاً غیرقابل‌حدس با هر تعداد تلاش معقول). برای همین،
Endpoint `POST /auth/reset-password` از همان زیرساخت اثبات‌شده قفل موقت
ورود (`app/core/rate_limit.py` - امن در برابر چند Worker، چون شمارنده‌ها
در دیتابیس نگه داشته می‌شوند نه حافظه) استفاده می‌کند - این‌بار کلید‌شده
بر اساس IP کلاینت (`reset-password:{ip}`) به‌جای نام‌کاربری، چون یک کد
نادرست به‌تنهایی هیچ کاربر مشخصی را معرفی نمی‌کند.

## `PasswordResetToken.channel`

فیلد جدید (`email`/`sms`) فقط برای گزارش/شفافیت نگه داشته می‌شود - منطق
اعتبارسنجی خودِ توکن (`reset_password()` در `password_reset_service.py`)
برای هر دو کانال یکسان است؛ همان ستون `token` هم برای رشته طولانی ایمیل
و هم برای کد ۶ رقمی پیامک استفاده می‌شود.

## Endpoint ها

- `POST /auth/forgot-password`: حالا `channel` ("email" یا "sms") قبول
  می‌کند؛ پیام موفقیت بر اساس کانال متفاوت است (اما همان اصل امنیتی
  «همیشه یک پیام یکسان، صرف‌نظر از معتبربودن شناسه» حفظ می‌شود).
- `GET/PUT /system/sms-settings` + `POST /system/sms-settings/test`
  (پیامک آزمایشی با کد ثابت `000000`).

## Frontend

`SmsSettings.jsx` (در «تنظیمات سامانه»، کنار `SmtpSettings.jsx` موجود) -
انتخاب روش ارسال با فیلدهای شرطی (کد الگو فقط برای Pattern، متن پیام
فقط برای Webservice) + دکمه تست.

`ForgotPasswordPage.jsx` بازنویسی شد: یک `ToggleButtonGroup` برای انتخاب
کانال (ایمیل/پیامک) اضافه شد؛ بعد از درخواست موفق پیامکی، به‌جای پیام
ساده، یک فرم «کد تأیید + رمز عبور جدید + تکرار» نمایش داده می‌شود که
مستقیماً همان Endpoint بازنشانی موجود (`/auth/reset-password`) را صدا
می‌زند.

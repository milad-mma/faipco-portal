# مدیریت مستقیم دیتابیس با pgAdmin 4

معادل PostgreSQL برای phpMyAdmin — مدیریت مستقیم جداول، اجرای Query، مشاهده
داده. **فقط برای Admin/توسعه‌دهنده، نه بخشی از خودِ پرتال** — پرسنل عادی
هیچ ارتباطی با این ابزار ندارند و هیچ لینکی از داخل پنل پرتال بهش وصل نیست.

## نصب

```bash
sudo bash install-pgadmin.sh --allowed-network 192.168.99.0/24
```

اسکریپت خودش تعاملی ایمیل و رمز عبور ورود به pgAdmin را می‌پرسد (اگر با
`--admin-email`/`--admin-password` از قبل نداده باشید). `--allowed-network`
را حتماً با رنج واقعی شبکه محلی خودتان (فرمت CIDR) عوض کنید.

## چرا Docker، نه نصب مستقیم با pip

اولین نسخه این اسکریپت با pip + Gunicorn (دقیقاً معماری خودِ Backend
پرتال) نصب می‌کرد. بعد از چند مشکل واقعی که یکی‌یکی روی همین سرور کشف
شد، به ایمیج رسمی Docker خودِ تیم pgAdmin (`dpage/pgadmin4`) سوییچ شد —
چون این ایمیج مستقیماً توسط سازندگان pgAdmin نگه‌داری می‌شود و این مسیرها
را از قبل درست پیکربندی کرده، نه چیزی که باید دستی کشفش می‌کردیم.

### مشکلاتی که با روش pip پیش آمد (برای مرجع آینده)

اگر روزی به نصب مستقیم (غیر Docker) برگشتید، این نکات را در نظر بگیرید:

1. **کندی نصب**: `pip install pgadmin4` بدون محدودیت نسخه روی
   `psycopg[binary]`، می‌تواند چند دقیقه (یا خیلی بیشتر) طول بکشد و هیچ
   پیشرفتی هم نشان ندهد — یک باگ Resolver شناخته‌شده در خودِ pip (نه یک
   خرابی)، وقتی مجبور می‌شود ده‌ها نسخه را یکی‌یکی امتحان کند.
2. **دیتابیس تنظیمات خودکار ساخته نمی‌شود**: `pgadmin4-cli add-user` در
   حالت CLI عمداً از ساخت خودکار SQLite از صفر امتناع می‌کند (رفتار
   عمدی، نه باگ — تأییدشده در Issue #7266 خودِ پروژه pgAdmin4 روی
   GitHub). باید اول `setup.py setup-db` اجرا شود.
3. **مسیرهای داخلی کشف‌نشده**: مسیرهایی مثل `AZURE_CREDENTIAL_CACHE_DIR`
   به‌طور پیش‌فرض زیرشاخه‌ای از `DATA_DIR` هستند — اگر `DATA_DIR` را
   صریح تنظیم نکنید، با خطای «مسیر وجود ندارد» شکست می‌خورد.
4. **رمز عبور پرسیده‌شده تعاملی با رمز نمایشی یکی نیست**: وقتی دیتابیس
   واقعاً اولین‌بار ساخته می‌شود، `setup-db` خودش تعاملی ایمیل/رمز
   می‌پرسد. Pipe کردن ورودی برای این پرسش قابل‌اعتماد نیست، چون ایمیل با
   `input()` خوانده می‌شود (با Pipe کار می‌کند) ولی رمز عبور با
   `getpass()` خوانده می‌شود — و `getpass()` عمداً تلاش می‌کند مستقیم از
   ترمینال واقعی (`/dev/tty`) بخواند، نه از Pipe. راه‌حل درست
   (تأییدشده مستقیم از سازنده pgAdmin در ایمیل رسمی پروژه):
   Environment Variable های `PGADMIN_SETUP_EMAIL`/`PGADMIN_SETUP_PASSWORD`.
5. **صفحه ورود فقط Refresh می‌شود، لاگین انجام نمی‌شود**: یک مشکل بسیار
   رایج و مستندشده در نصب‌های pgAdmin پشت Reverse Proxy — CSRF/Session
   Cookie به‌خاطر سردرگمی برنامه درباره scheme/host واقعی (وقتی Nginx
   به‌عنوان واسط قرار می‌گیرد) به‌درستی تنظیم نمی‌شود.

Docker با ایمیج رسمی، همه این‌ها را از پیش حل کرده — برای همین جایگزین شد.

### چرا `--network=host`

PostgreSQL خودِ پرتال روی همین سرور نصب است (نه در یک کانتینر دیگر). با
شبکه Bridge پیش‌فرض Docker، «localhost» داخل کانتینر به خودِ کانتینر
اشاره می‌کند، نه به این سرور — یعنی اتصال کانتینر به PostgreSQL میزبان
می‌تواند کاملاً غیرقابل‌اعتماد باشد (یک مشکل واقعی و رایج، حتی در بحث‌های
رسمی جامعه Docker). با `--network=host`، این کانتینر دقیقاً همان
Namespace شبکه‌ای خودِ سرور را به اشتراک می‌گذارد — یعنی از داخل pgAdmin،
`localhost:5432` دقیقاً همانی است که در نصب مستقیم (غیر Docker) هم بود.

چون با `--network=host` نگاشت پورت (`-p`) اصلاً معنا ندارد، پورت داخلی
pgAdmin با Environment Variable رسمی خودشان (`PGADMIN_LISTEN_PORT`،
[مستندشده رسمی](https://www.pgadmin.org/docs/pgadmin4/latest/container_deployment.html))
مستقیم روی همان پورتی تنظیم می‌شود که می‌خواهیم — تا با هیچ سرویس دیگری
(مثلاً پورت ۸۰ خودِ Nginx پرتال) تداخل نکند.

## ⚠️ فقط از شبکه محلی — نه اینترنت

چون `--network=host` نگاشت IP-محور Docker (که در Bridge امکانش هست) را
ندارد، محدودیت IP فقط با یک لایه انجام می‌شود: قانون Firewall (`ufw`)
که فقط رنج شبکه محلی داده‌شده را به پورت pgAdmin اجازه می‌دهد — همه‌چیز
دیگر، حتی با IP/Port درست، رد می‌شود. این ابزار هرگز از طریق Reverse
Proxy خارجی پرتال routing نمی‌شود و هیچ Domain عمومی ندارد.

## بعد از نصب — چطور به دیتابیس پرتال وصل شویم (مرحله‌به‌مرحله)

1. از داخل شبکه محلی، به آدرسی که اسکریپت در پایان نصب چاپ کرد بروید —
   چیزی شبیه `http://192.168.99.6:5050`.
2. با ایمیل/رمزی که موقع نصب دادید (یا اسکریپت خودش تولید کرد) وارد شوید.
3. توی پنل چپ، روی **Servers** راست‌کلیک کنید → **Register** → **Server…**
4. تب **General**:
   - **Name**: هر اسمی دلخواه — مثلاً `FAIPCO Portal DB`
5. تب **Connection**:
   - **Host name/address**: `localhost` (یا `127.0.0.1`) — چون با
     `--network=host` نصب شده، این دقیقاً همان PostgreSQL خودِ سرور است
   - **Port**: `5432`
   - **Maintenance database**: `faipco_portal`
   - **Username**: `faipco_user`
   - **Password**: مقدار واقعی رمز دیتابیس — از خطِ `DATABASE_URL` در
     `backend/.env` روی سرور بخوانید (فرمت:
     `postgresql+asyncpg://faipco_user:RMZ@localhost:5432/faipco_portal`
     — بخش بین `:` و `@` همان رمز است)
   - تیک **Save password?** را بزنید تا هربار نپرسد
6. دکمه **Save** را بزنید — بلافاصله به دیتابیس وصل می‌شود و در پنل چپ،
   زیر Servers، درخت کامل جداول/Schema های پرتال را می‌بینید.

⚠️ رمز عبوری که اینجا برای اتصال به دیتابیس وارد می‌کنید، کاملاً **جدا**
از رمز ورود خودِ pgAdmin است (که در نصب تعیین کردید).

## نکات امنیتی مهم

- حساب کاربری pgAdmin که ساختید، بعد از وصل‌کردن سرور بالا، دسترسی کامل
  به **هر جدولی** در دیتابیس پرتال (شامل کد ملی، حقوق، اطلاعات کامل
  پرسنلی) دارد — رمز عبورش را با همان دقتی نگه دارید که رمز Admin خودِ
  پرتال را نگه می‌دارید.
- این ابزار عمداً از HTTPS استفاده نمی‌کند — چون فرض بر این است که فقط از
  شبکه داخلی و قابل‌اعتماد در دسترس است، نه اینترنت عمومی.

## عیب‌یابی

```bash
docker ps -a | grep pgadmin4        # آیا کانتینر در حال اجراست؟
docker logs pgadmin4 --tail 50      # آخرین لاگ‌ها
docker restart pgadmin4             # ری‌استارت
```

## حذف نصب

```bash
docker rm -f pgadmin4
sudo rm -rf /opt/pgadmin4-data
sudo ufw delete allow from 192.168.99.0/24 to any port 5050 proto tcp
```

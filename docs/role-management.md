# پنل مدیریت نقش/مجوز

قبلاً این پروژه هیچ Endpoint ای برای «ساخت نقش جدید» نداشت — پنل «مدیریت
دسترسی» فقط اجازه می‌داد یکی از نقش‌های *موجود* (که فقط از طریق Migration
یا دسترسی مستقیم دیتابیس ساخته می‌شدند) به یک کاربر تخصیص داده شود. این
محدودیت با یک پنل کامل مدیریت نقش/مجوز رفع شد.

## چه چیزی رفع شد، چه چیزی هنوز باقی می‌ماند

- ✅ حالا Admin می‌تواند از پنل، یک نقش **جدید** بسازد و از میان مجوزهای
  **موجود**، هرکدام را که خواست به آن نقش بدهد — بدون نیاز به Migration
  یا هیچ تغییر کدی، برای هر ترکیب تازه‌ای از مجوزهای از‌قبل‌موجود.
- ⚠️ ساخت یک مجوز **کاملاً جدید** (که تا امروز هیچ‌جای کد به آن Code گوش
  نمی‌دهد) همچنان فقط با یک تغییر کد ممکن است — چون یک Permission Code
  فقط وقتی معنای واقعی دارد که جایی از Backend با `require_permission(...)`
  دقیقاً همان رشته را چک کند. این محدودیت ذاتی سیستم است، نه یک نقص این
  پنل — هیچ رابط کاربری‌ای نمی‌تواند این را دور بزند، چون یک مجوز بدون
  کدی که به آن گوش بدهد، کاملاً بی‌اثر است.

## Backend

- `backend/app/schemas/user_management.py`: `PermissionOut`، `RoleDetailOut`، `RoleUpsertIn`
- `backend/app/services/user_management_service.py`: `list_permissions`،
  `get_role_detail`، `create_role`، `update_role`، `delete_role`
- `backend/app/api/v1/endpoints/users.py`: مسیرهای جدید زیر
  `/users/role-catalog` (⚠️ عمداً این نام، نه `/users/roles/{id}` — چون
  آن مسیر از قبل برای حذف یک *انتصاب* نقش استفاده می‌شد؛ استفاده مجدد از
  همان الگو برای حذف خودِ *تعریف* نقش با همان متد HTTP باعث تداخل مسیر
  می‌شد)

### محافظت‌های ساخته‌شده در Service

- نام «superadmin» کاملاً غیرقابل‌ویرایش/حذف است — چون جای دیگری از کد
  (منطق مسدودسازی تخصیص نقش) دقیقاً همین رشته را چک می‌کند.
- ⚠️ **به‌روزرسانی بعدی**: طبق درخواست صریح، `is_system=True` دیگر مانع
  **ویرایش** نیست — چون نقش‌هایی که پیش از این پنل مستقیماً از دیتابیس
  ساخته شده بودند (مثل site_manager، hr-manager) با `is_system=True`
  ذخیره شده بودند و کارفرما نیاز داشت همان‌ها را هم ویرایش کند.
  `is_system=True` همچنان مانع **حذف** است (پیش‌فرض ایمن‌تر).
- حذف یک نقش که هم‌اکنون به حداقل یک کاربر اختصاص دارد مسدود می‌شود — نه
  حذف خاموش با CASCADE (که بدون هیچ هشداری، دسترسی همه آن افراد را
  می‌گرفت). Admin باید اول خودش آگاهانه انتصاب‌ها را از صفحه «مدیریت
  دسترسی» بردارد.
- نام تکراری نقش رد می‌شود.

### مجوزهای سطح ادمین قابل‌تخصیص به هر نقش

مجوزهایی که قبلاً فقط Admin واقعی (`is_superuser`) از آن‌ها استفاده
می‌کرد (مثل `sites.manage`، `vehicles.manage`) از نظر Backend همیشه
قابل تخصیص به هر نقشی بوده‌اند — چون `require_permission()` فقط چک
می‌کند «آیا این کاربر نقشی دارد که این مجوز را داشته باشد»، نه اینکه
مخصوص Admin باشد. تنها تغییر، یک برچسب هشدار در Frontend است: هر مجوزی
که با `.manage` تمام شود یا با `system.` شروع شود، در چک‌باکس‌لیست پنل
مدیریت نقش/مجوز، یک نشان «دسترسی ادمین» کنارش نشان داده می‌شود — تا
Admin آگاهانه تصمیم بگیرد آیا واقعاً می‌خواهد این سطح دسترسی گسترده را
به یک نقش دیگر هم بدهد یا نه.

## Frontend

`RoleManagementPage.jsx` (`/role-management`، زیرمجموعه «مدیریت دسترسی»
در پنل Admin): لیست نقش‌ها + Dialog ساخت/ویرایش (نام، توضیح، چک‌باکس‌لیست
مجوزها — گروه‌بندی‌شده بر اساس پیشوند مثل `notices.*`، `vehicles.*` برای
خوانایی بهتر) + Dialog تأیید حذف.

## دور سوم — منوها واقعاً بر اساس مجوز نمایش داده می‌شوند

طبق بازخورد کاربر («اگر مجوزی به یک نقش دادم، منوش هم باید اضافه بشه»)،
مشخص شد بعضی صفحات ادمینی (سایت‌ها، همگام‌سازی، مدیریت دسترسی، خودِ همین
پنل مدیریت نقش/مجوز، پشتیبان‌گیری، رنج‌های IP مجاز) با `AdminRoute`
محافظت می‌شدند — که مستقیماً `is_superuser` را چک می‌کند، نه مجوز واقعی.
یعنی حتی اگر یک نقش غیر-Admin مجوز متناظر (مثل `sites.manage`) را
داشت، نه منویی برایش نشان داده می‌شد، نه خودِ مسیر برایش باز می‌شد — با
اینکه Backend از قبل این مجوز را درست چک می‌کرد.

### رفع

- شش فلگ جدید در `get_me()` (`can_manage_sites`، `can_manage_sync`،
  `can_manage_users`، `can_manage_roles`، `can_manage_ip_allowlist`،
  `can_manage_backup`) — هرکدام دقیقاً منطبق با همان Permission Code که
  Backend همان صفحه را با آن چک می‌کند.
- مسیرهای مربوطه در `App.jsx` از `AdminRoute` به `PermissionRoute` (با
  همان فلگ) تغییر کردند.
- `NAV_ITEMS` در `Layout.jsx`: از `adminOnly: true` به `requiresX: true`
  تغییر کردند — یک نکته ظریف: آیتم والد «مدیریت دسترسی» چهار زیرمنوی
  متفاوت با مجوزهای متفاوت دارد؛ برای اینکه کسی با فقط یکی از این چهار
  مجوز هم بتواند به آن زیرمنوی خاص برسد، والد با شرط OR (هر یک از چهار
  مجوز) نمایش داده می‌شود و اگر کاربر خودِ `/access` را نداشته باشد ولی
  به یک زیرمنو دسترسی داشته باشد، کلیک روی والد به همان زیرمنو می‌رود
  (نه به `/access` که برایش بسته است).
- **مهم‌ترین بخش**: چون پرسنل غیر-Admin اصلاً منوی کناری Admin
  (Layout.jsx) را نمی‌بینند (فقط نوار پایین)، این شش آیتم به
  `EXTRA_ACCESS_ITEMS` در `ProfilePage.jsx` («دسترسی‌های ویژه») هم اضافه
  شدند — این تنها جایی است که یک پرسنل غیر-Admin واقعاً این صفحات را
  می‌بیند و به آن‌ها می‌رسد.

### آنچه عمداً تغییر نکرد

صفحات «داشبورد»، «بررسی و اعمال آپدیت»، «پرسنل آنلاین» همچنان فقط برای
Admin واقعی هستند — چون Permission Code مجزا و قابل‌تفویضی برایشان
تعریف نشده. («پرسنل» در دور بعدی این مستند تبدیل به مجوز-محور شد —
پایین‌تر ببینید.)

## دور چهارم — تکمیل بررسی جامع + رفع دو باگ ریشه‌ای

### مجوزهایی که تا امروز چک می‌شدند ولی هیچ فلگ Frontend نداشتند

یک بررسی کامل (`grep` روی همه `require_permission(...)` در Backend) نشان
داد چند مجوز دیگر هم دقیقاً همین مشکل را داشتند — چک واقعی در Backend
وجود داشت، ولی هیچ راهی برای رسیدن به آن‌ها از UI نبود:

- `employees.update` → `can_update_employees`
- `vehicles.manage` → `can_manage_vehicles` (⚠️ باگ واقعی: دکمه‌های
  ویرایش/حذف در گزارش خودروها تا امروز فقط `is_superuser` را چک
  می‌کردند، نه این مجوز — یعنی حتی اگر نقشی این مجوز را می‌گرفت، دکمه‌ها
  همچنان مخفی می‌ماندند. رفع شد.)
- `sync.view`، `sync.run` → `can_view_sync`، `can_run_sync` (قبلاً صفحه
  «همگام‌سازی» فقط با `sync.manage` باز می‌شد؛ حالا هر سه مجوز مرتبط راه می‌دهند)
- `system.cache_bust` → `can_bust_cache` (داخل همان صفحه «پشتیبان‌گیری»)

`employees.view` و `employees.create` هم در دیتابیس وجود داشتند ولی
**هیچ‌کدام واقعاً در هیچ کدی چک نمی‌شدند** — فقط به‌عنوان مثال در یک
Docstring (`app/models/user.py`) ذکر شده بودند. اینها حالا واقعاً وصل
شدند (پایین‌تر توضیح داده شده).

### قابلیت جدید: افزودن دستی پرسنل (`employees.create`)

⚠️ **نکته معماری مهم**: مدل `Employee` صراحتاً مستندسازی شده بود که
«رکوردهای این جدول توسط Sync Engine پر می‌شوند و مستقیماً توسط کاربر
Insert نمی‌شوند». قبل از پیاده‌سازی، منطق Upsert خودِ Sync Engine بررسی
شد: چون بر اساس `(site_id, personnel_code)` تطبیق می‌دهد، اگر بعداً
همان کد پرسنلی در منبع Sync واقعی هم ظاهر شود، رکورد دستی به‌طور طبیعی
به‌روزرسانی/ادغام می‌شود — نه خطا یا تکراری. با این اطمینان، پیاده‌سازی شد:

- **Migration 033**: ستون `is_manually_created` (فقط برای شفافیت/گزارش،
  در رفتار Sync اثری ندارد) + مجوزهای `employees.view`/`employees.create`.
- **`POST /employees`** (`require_permission("employees.create")`) —
  کد پرسنلی+سایت تکراری رد می‌شود؛ ایزوله‌سازی چندسایتی کامل (Admin هر
  سایتی، غیر-Admin فقط سایت‌های مجاز خودش).
- **Frontend**: دکمه «افزودن دستی پرسنل» در صفحه «پرسنل» (فقط اگر
  `can_create_employees`) با یک Dialog کامل (نام، کد پرسنلی، سایت، واحد
  اختیاری، سمت اختیاری، کد ملی/موبایل اختیاری).

### دو باگ ریشه‌ای در سیستم انتصاب نقش (کشف‌شده حین رفع درخواست سایت‌اسکوپ اجباری)

کاربر گزارش داد نقش «حراست» را «سراسری» دیده — بررسی نشان داد **دو باگ
واقعی و مستقل** علتش بودند، نه فقط نبود اعتبارسنجی:

1. **`AssignAccessDialog.jsx`**: فیلد انتخاب سایت فقط برای نقشی که
   دقیقاً نامش `"site_manager"` بود نمایش داده می‌شد! برای هر نقش دیگری
   (مثل «حراست»)، این فیلد اصلاً روی صفحه نبود — پس انتصاب همیشه بی‌صدا
   سراسری (`site_id=null`) ثبت می‌شد، حتی وقتی Admin هرگز چنین قصدی
   نداشت. رفع شد: این فیلد حالا برای **همه** نقش‌ها نمایش داده می‌شود و
   اجباری است.
2. **`bulk_assign_role` (Backend)**: حتی وقتی Admin با فیلتر «فقط پرسنل
   سایت X» یک نقش را دسته‌جمعی اختصاص می‌داد، خودِ تابع همیشه
   `UserRole(site_id=None)` می‌ساخت — کاملاً مستقل از فیلتر انتخاب‌شده!
   رفع شد: اگر فیلتر `site_id` داده شده، همان برای انتصاب هم استفاده
   می‌شود؛ اگر با فهرست مستقیم `employee_id` (بدون فیلتر سایت) کار
   می‌شود، سایت خودِ هر پرسنل به‌طور جداگانه به کار می‌رود.
3. **`AssignRoleIn.site_id`** (Backend، انتصاب تکی) از اختیاری به
   اجباری تغییر کرد — دیگر امکان انتصاب سراسری از این مسیر وجود ندارد.

⚠️ **دامنه این رفع**: فقط مسیرهای «آینده» (انتصاب‌های جدید) را درست
می‌کند؛ انتصاب‌های سراسری *موجود* در دیتابیس دست‌نخورده باقی می‌مانند
(بدون Migration خودکار برای تبدیلشان) — چون تبدیل خودکار به «انتصاب
جداگانه به هر سایت» بدون تصمیم آگاهانه Admin می‌توانست خطرناک باشد. اگر
لازم است، از همان صفحه «مدیریت دسترسی»، این انتصاب‌های قدیمی (که حالا
با برچسب «سراسری — قدیمی» به‌وضوح مشخص شده‌اند) قابل حذف و دوباره‌سازی
درست‌اند.

## دور پنجم — یک باگ حیاتی که خودِ همین سایت‌اسکوپ اجباری فاش کرد

بعد از اجباری‌شدن site_id، کاربران گزارش دادند نقشی که همه مجوزها را
داشت، **هیچ‌کدام** از آن مجوزها را در پنل کاربری نشان نمی‌داد — و بعداً
حتی وقتی نقش‌های قدیمی (مدیر میانی/مدیر حسابداری) با انتصاب دوباره و
سایت مشخص جایگزین شدند، دسترسی «ارسال فیش حقوقی» هم از دست رفت.

### علت ریشه‌ای

`get_permission_codes(user_id, site_id=None)` — طبق مستندات خودش —
وقتی site_id داده نشود، **فقط انتصاب‌های سراسری** را می‌بیند. این رفتار
از قبل مستند و شناخته‌شده بود (حتی یک کامنت در `attendance.py` صراحتاً
به آن اشاره می‌کرد). اما از وقتی site_id برای انتصاب نقش اجباری شد،
دیگر هیچ انتصاب جدیدی سراسری نیست — یعنی هر جای کد که این تابع را
**بدون** site_id صدا می‌زد (برای پرسیدن «آیا این کاربر اصلاً این
قابلیت را دارد»، نه «برای این سایت خاص»)، همیشه پاسخ منفی می‌داد.

### رفع — یک تابع جدید + جایگزینی در هر جای درست

اضافه شد: `get_all_permission_codes(user_id)` — همه مجوزهای کاربر از
هر انتصاب نقشی (سراسری + هر سایتی)، بدون فیلتر سایت. جایگزین شد در **هر
جایی که واقعاً یک بررسی «قابلیت» بود، نه بررسی «برای این سایت مشخص»**:

- `get_me()` در `auth_service.py` (فلگ‌های can_X که منوهای پنل کاربری را کنترل می‌کنند)
- `require_permission()` در `deps.py` — فقط در حالت پیش‌فرض
  (`site_scoped=False`)؛ حالت `site_scoped=True` دست‌نخورده ماند چون
  آن‌جا واقعاً باید محدود به یک سایت خاص بماند
- بررسی مجوز WebSocket حضور در `attendance.py`
- **`_has_permission()` در `notice_service.py`** — دقیقاً همان جایی که
  باعث از‌دست‌رفتن «ارسال فیش حقوقی» شده بود. این تابع هم برای
  بررسی‌های واقعاً سایت‌محور (`notices.target.site/department/employee`
  — که site_id مشخص می‌گیرند و درست است محدود بمانند) هم برای
  بررسی‌های سطح «قابلیت» (`notices.payroll`، `notices.attendance_card`،
  `notices.target.all`، `notices.target.role` — که site_id نمی‌گیرند)
  استفاده می‌شود؛ فقط حالت دوم اصلاح شد.

یک بررسی جامع (`grep` روی هر فراخوانی باقی‌مانده `get_permission_codes`
در کل Backend) تأیید کرد هیچ فراخوانی دیگری با این الگوی معیوب باقی
نمانده — هر فراخوانی باقی‌مانده حالا site_id واقعی و معنادار می‌فرستد.
دو تابع مرتبط دیگر (`get_sites_with_permission`، `get_accessible_site_ids`)
هم بررسی شدند و از اول درست بودند (مستقیم روی `UserRole` کوئری می‌زنند،
نه از طریق تابع معیوب).

## دور ششم — قابلیت «تنظیمات سامانه» + عکس پس‌زمینه صفحه ورود

یک قابلیت جدید و مستقل: مجوز `system.settings` (Migration 034) + یک
منوی جدید «تنظیمات سامانه» (فعلاً فقط عکس پس‌زمینه صفحه ورود، ولی محل
طبیعی هر تنظیم سراسری آینده).

### چرا بدون Migration جدید برای خودِ ذخیره‌سازی عکس؟

از همان جدول عمومی `SystemSetting` (کلید/مقدار، از قبل موجود برای
تنظیماتی مثل فاصله Sync خودکار) استفاده شد — محتوای عکس Base64-شده در
`value` (نوع Text، بدون محدودیت طول عملی در PostgreSQL) ذخیره می‌شود.
این دقیقاً همان الگوی عکس پرسنلی (`Employee.photo_thumbnail`، باینری
مستقیم در دیتابیس) است، فقط چون این یکی باید **قبل از ورود** هم در
دسترس باشد (صفحه ورود، نه یک صفحه پشتِ احراز هویت)، Base64 در متن به‌جای
یک ستون Binary جدا انتخاب شد — بدون نیاز به یک مسیر ذخیره‌سازی فایل
جداگانه یا Migration.

- **`GET /system/login-background`**: عمداً بدون هیچ احراز هویتی — اگر
  چیزی تنظیم نشده، ۴۰۴ می‌دهد.
- **`POST`/`DELETE`**: فقط با `require_permission("system.settings")`.
- **Frontend**: `LOGIN_BACKGROUND_URL` مستقیماً به‌عنوان CSS
  `background-image` صفحه ورود استفاده می‌شود — بدون بررسی جداگانه با
  JS؛ اگر عکسی تنظیم نشده (۴۰۴)، مرورگر خودش بی‌صدا نادیده می‌گیرد و
  همان رنگ ثابت پیش‌فرض دیده می‌شود، بدون خطا یا چشمک‌زدن.

## دور هفتم — دو اصلاح ظاهری کوچک

- **متن سفید داخل پلاک در حالت تیره**: فیلدهای ورودی پلاک (`IranianLicensePlateInput.jsx`)
  رنگ متن را از تِم به ارث می‌بردند (که در حالت تیره روشن/سفید می‌شود)،
  با اینکه پس‌زمینه پلاک همیشه ثابت سفید بود. رنگ متن هم صریحاً ثابت شد.
- **وسط‌چین‌نبودن صفحه «خودروهای من» در دسکتاپ**: `mx: "auto"` اضافه شد
  — هماهنگ با بقیه صفحات.




## دور هشتم — «گزارش اطلاعیه‌های سایت» از Hard-code به مجوز واقعی

تا امروز، «گزارش اطلاعیه‌های سایت من» (`/notice-reports`) مستقیماً به
نام نقش `site_manager` Hard-code شده بود — نه دو جای مختلف: هم فلگ
`can_view_site_notice_report` در `get_me()`، هم خودِ Endpoint داده
(`GET /notices/site-report`). یعنی حتی اگر Admin یک نقش دیگر می‌ساخت و
از پنل «مدیریت نقش/مجوز» هر مجوزی به آن می‌داد، **امکان تخصیص همین
قابلیت خاص اصلاً وجود نداشت** — چون کد دنبال یک Permission نمی‌گشت،
دنبال دقیقاً همین رشته نام نقش می‌گشت.

### رفع

- **Migration 035**: مجوز جدید `notices.site_report` ساخته و به‌طور
  پیش‌فرض به همان نقش `site_manager` هم وصل شد — برای این‌که تجربه کسانی
  که همین الان این نقش را دارند، دقیقاً همان‌طور که بود باقی بماند.
- **`get_me()`**: به‌جای `get_managed_site_ids(user_id, "site_manager")`
  (که مستقیماً نام نقش را چک می‌کرد)، حالا از `get_sites_with_permission`
  (همان الگوی استاندارد پروژه برای مجوزهای سایت‌محور، مثل
  `vehicles.view_all`) استفاده می‌کند.
- **`GET /notices/site-report`**: همان تغییر، در خودِ Endpoint داده
  (نه فقط فلگ منو) — چون رفع‌کردن فقط فلگ بدون رفع خودِ Endpoint، باعث
  می‌شد منو نمایش داده شود ولی خودِ گزارش با ۴۰۳ رد شود.

از این به بعد، Admin می‌تواند از پنل «مدیریت نقش/مجوز»، مجوز
`notices.site_report` را به هر نقش دیگری هم بدهد — بدون هیچ تغییر کدی.

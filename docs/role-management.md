# پنل مدیریت نقش/مجوز

قبلاً این پروژه هیچ Endpoint ای برای «ساخت نقش جدید» نداشت — پنل «مدیریت
دسترسی» فقط اجازه می‌داد یکی از نقش‌های *موجود* (که فقط از طریق Migration
یا دسترسی مستقیم دیتابیس ساخته می‌شدند) به یک کاربر تخصیص داده شود. این
محدودیت با یک پنل کامل مدیریت نقش/مجوز رفع شد.

## چه چیزی رفع شد، چه چیزی هنوز باقی می‌ماند

- ✅ حالا Admin می‌تواند از پنل، یک نقش **جدید** بسازد و از میان مجوزهای
  **موجود**، هرکدام را که خواست به آن نقش بدهد — بدون نیاز به Migration
  یا هیچ تغییر کدی، برای هر ترکیب تازه‌ای از مجوزهای از‌قبل‌موجود.
- ⚠️ ساخت یک مجوز **کاملاً جدید** (که تا امروز هیچ‌جای کد به آن Code گوش
  نمی‌دهد) همچنان فقط با یک تغییر کد ممکن است — چون یک Permission Code
  فقط وقتی معنای واقعی دارد که جایی از Backend با `require_permission(...)`
  دقیقاً همان رشته را چک کند. این محدودیت ذاتی سیستم است، نه یک نقص این
  پنل — هیچ رابط کاربری‌ای نمی‌تواند این را دور بزند، چون یک مجوز بدون
  کدی که به آن گوش بدهد، کاملاً بی‌اثر است.

## Backend

- `backend/app/schemas/user_management.py`: `PermissionOut`، `RoleDetailOut`، `RoleUpsertIn`
- `backend/app/services/user_management_service.py`: `list_permissions`،
  `get_role_detail`، `create_role`، `update_role`، `delete_role`
- `backend/app/api/v1/endpoints/users.py`: مسیرهای جدید زیر
  `/users/role-catalog` (⚠️ عمداً این نام، نه `/users/roles/{id}` — چون
  آن مسیر از قبل برای حذف یک *انتصاب* نقش استفاده می‌شد؛ استفاده مجدد از
  همان الگو برای حذف خودِ *تعریف* نقش با همان متد HTTP باعث تداخل مسیر
  می‌شد)

### محافظت‌های ساخته‌شده در Service

- نام «superadmin» کاملاً غیرقابل‌ویرایش/حذف است — چون جای دیگری از کد
  (منطق مسدودسازی تخصیص نقش) دقیقاً همین رشته را چک می‌کند.
- ⚠️ **به‌روزرسانی بعدی**: طبق درخواست صریح، `is_system=True` دیگر مانع
  **ویرایش** نیست — چون نقش‌هایی که پیش از این پنل مستقیماً از دیتابیس
  ساخته شده بودند (مثل site_manager، hr-manager) با `is_system=True`
  ذخیره شده بودند و کارفرما نیاز داشت همان‌ها را هم ویرایش کند.
  `is_system=True` همچنان مانع **حذف** است (پیش‌فرض ایمن‌تر).
- حذف یک نقش که هم‌اکنون به حداقل یک کاربر اختصاص دارد مسدود می‌شود — نه
  حذف خاموش با CASCADE (که بدون هیچ هشداری، دسترسی همه آن افراد را
  می‌گرفت). Admin باید اول خودش آگاهانه انتصاب‌ها را از صفحه «مدیریت
  دسترسی» بردارد.
- نام تکراری نقش رد می‌شود.

### مجوزهای سطح ادمین قابل‌تخصیص به هر نقش

مجوزهایی که قبلاً فقط Admin واقعی (`is_superuser`) از آن‌ها استفاده
می‌کرد (مثل `sites.manage`، `vehicles.manage`) از نظر Backend همیشه
قابل تخصیص به هر نقشی بوده‌اند — چون `require_permission()` فقط چک
می‌کند «آیا این کاربر نقشی دارد که این مجوز را داشته باشد»، نه اینکه
مخصوص Admin باشد. تنها تغییر، یک برچسب هشدار در Frontend است: هر مجوزی
که با `.manage` تمام شود یا با `system.` شروع شود، در چک‌باکس‌لیست پنل
مدیریت نقش/مجوز، یک نشان «دسترسی ادمین» کنارش نشان داده می‌شود — تا
Admin آگاهانه تصمیم بگیرد آیا واقعاً می‌خواهد این سطح دسترسی گسترده را
به یک نقش دیگر هم بدهد یا نه.

## Frontend

`RoleManagementPage.jsx` (`/role-management`، زیرمجموعه «مدیریت دسترسی»
در پنل Admin): لیست نقش‌ها + Dialog ساخت/ویرایش (نام، توضیح، چک‌باکس‌لیست
مجوزها — گروه‌بندی‌شده بر اساس پیشوند مثل `notices.*`، `vehicles.*` برای
خوانایی بهتر) + Dialog تأیید حذف.
